## Plan Decisions
- PD-001 [AC-001] [FR-001] complete: Add `TouchSet.generatedTokens (generated: Set<string>) (tokens: string list) : string list` to `FS.GG.Coord.Core/TouchSet.fs`/`.fsi` — pure, no IO. It stems each requested token (reusing the existing `stem` function) and returns the subset whose stem is an EXACT member of `generated`. A directory-prefix token (e.g. `registry/**`, stem `registry`) never matches a file-shaped generated entry (e.g. `registry/driver-skill-manifest.json`), which is what keeps the ADR-0044 #309 parent-directory trap (documented on `tokensOverlap`) from reopening: only an exact-name declaration of the generated artifact itself is caught.
- PD-002 [AC-002] [FR-002] complete: In `Client.fs`'s `updateTouchSet` (backs both `widen` and `set-paths`), after `Writes.validate` accepts the requested tokens and before the proposed declaration or collision scan is computed, resolve the generated set via the existing `generatedPathCollector`/`KitDigest.kitRoot()` seam (already wired for `deliveryPathsVerified`) and call `TouchSet.generatedTokens`. A non-empty result refuses the whole call — no PATCH is issued, `Paths:` stays byte-identical, and the message names ADR-0044 and every offending token, mirroring the existing fail-loud style of the flag-shaped/sentinel-mixed refusals in `Writes.validate`. This is an ALL-OR-NOTHING input refusal (same shape as `Writes.validate`'s own refusals), not a per-token silent drop, because a silent drop would leave a worker believing they declared something they did not (clarify decision, `work/2305-generated-artifact-lanes/clarifications.md`).
- PD-003 [AC-001] [FR-003] complete, CORRECTED IN REPAIR 1: Add `TouchSet.excludeGenerated (generated: Set<string>) (pairs: (string * string) list) : (string * string) list` to `TouchSet.fs`/`.fsi` — pure. It drops a `(x, y)` conflict pair only when `stem x = stem y` AND that shared stem is a member of `generated`; an asymmetric pair (one side a directory prefix, the other an exact generated file) is NOT dropped, for the same #309 reason as PD-001. Wired into `Client.fs` at the two places `TouchSet.conflicts`/`TouchSet.scopedConflicts` fed a verdict straight through before this change: the per-candidate scan inside `activeCollisions` (used by `widen`/`set-paths`'s pre-PATCH recheck) and `overlapCmd`'s two-ref comparison.
  **This entry's original text claimed `Lanes.fs` and `Schedulability.fs` were "deliberately NOT touched... because PD-002 stops a generated token from ever entering a declaration, [so] the scheduler's own lane partitioning never sees the collision to begin with."** The independent critic's round-1 review (PR #2370) proved that premise false by EXECUTION: two throwaway xUnit facts against the compiled `FS.GG.Coord.Core.dll` showed `Lanes.partition` still fused the `.github#2254`/`.github#2248`-shaped pair into ONE lane and `Schedulability.schedulable` still returned `OverlapsInFlight` for it — the exact pair `overlapCmd` already reported DISJOINT. The gap: PD-002's refusal only closes the door on a token entering a declaration going FORWARD, through `widen`/`set-paths`; it does not retroactively clear a token an item's ORIGINAL `Paths:` line already names (see PD-009 — `.github#2216` is live proof this path exists), and even a token that DID only ever arrive through `widen` would still reach `Lanes.partition`/`Schedulability.schedulable` unfiltered, because those two functions call `TouchSet.conflicts`/`scopedConflicts` directly and neither was ever taught about `excludeGenerated`. AC-1's own text — "two items... can hold concurrent **lanes**" — names the noun `Lanes.fs` computes, so a fix that never reaches it does not meet the acceptance criterion the row states, regardless of what `overlap` says. See PD-007 for the actual repair.
- PD-004 [AC-001] [FR-004] complete: No new code — this is the negative-case proof that PD-001/PD-003's exact-stem-match rule does not accidentally clear a real collision. Covered by `TouchSetTests.fs` cases: (a) two DIFFERENT real (non-generated) files sharing no token still overlap normally; (b) a generated exact-match token on one side against a directory-prefix declaration on the other (e.g. `registry/**`) still collides, proving the parent-directory case stays caught.
- PD-005 [AC-001] [FR-005] complete: No code change — `src/FS.GG.Kit/FS.GG.Kit.csproj` is verified absent from `scripts/generated-paths`' output (measured: `scripts/generated-paths` lists `dist/skill-union-assert.sh`, `registry/coordination-kit-skill-manifest.json`, `registry/driver-skill-manifest.json`, `registry/repos.lock` — no kit csproj), so `TouchSet.generatedTokens`/`excludeGenerated` never match it and `check-kit-published-coherence`'s single-writer field keeps colliding exactly as today. Proven by a `TouchSetTests.fs` case using the real generated set shape.
- PD-006 [AC-003] [FR-006] complete: No code change to `scripts/generate-driver-manifest` — ADR-0044's `--list` contract is already implemented correctly (verified: both manifest paths are already emitted, whole-file/empty-marker). Proof is by EXECUTION per the item's own gate-inversion requirement: dirty a committed manifest (or edit a skill body without regenerating) and confirm `scripts/generate-driver-manifest --check` exits non-zero, run manually in the worktree and recorded under `Verification:` in the delivery report — the item's declared `Paths:` includes this script defensively but its ADR-0044 compliance predates this change and needs no edit.
- PD-007 [AC-001] [FR-003] complete, ADDED IN REPAIR 1: Thread a `generated: Set<string>` parameter into `Schedulability.schedulable` (FIRST parameter) and `Lanes.partition` (FIRST parameter), applying `TouchSet.excludeGenerated generated` to each function's own disjointness/conflict computation — the same rule PD-003 states, now reaching the two functions AC-1 actually names. This is a REAL, NON-ADDITIVE `FS.GG.Coord.Core` signature change (correcting PC-001 below), because both functions are called with fixed arity by production code and tests; there is no additive/optional-parameter form for a plain `let`-bound F# function. `Batch.scheduleWith`/`Batch.schedule` (`FS.GG.Coord.Core/Batch.fs`) gain the same leading parameter and thread it straight to `schedulable`, since that is `take`/`batch`/`next`'s real call path (`Client.renderLiveDecision` → `Batch.scheduleWith` → `Schedulability.schedulable`) — fixing `Schedulability.schedulable` alone without threading through `Batch` would have left the live scheduling commands unfixed even though the pure function was correct in isolation.
  Live IO callers get the REAL roster: `Client.fs`'s `renderLiveDecision` — the function `take`/`batch`/`next` share (see its own doc: "Live board commands use `renderLiveDecision`") — resolves `generated` via the same collector seam the widen-time refusal above already uses, and passes it to `Batch.scheduleWith`. This is what closes the PRACTICAL gap, not merely the provable one: a live `take`/`batch` no longer refuses two items whose real subjects never collided.
  Pure/offline callers pass `Set.empty`, explicitly, not silently: `Program.fs`'s `lanes` and `decide` commands read a caller-supplied snapshot from stdin and have no filesystem to ask `scripts/generated-paths` of — they are the CLI's own pure DECISION half (see the module's header distinction between DECISION and IO commands), the same position `Client.fs`'s pre-existing `renderDecision` ("Pure snapshot projection retained for offline diagnostics") already occupies. `Set.empty` reproduces the exact pre-#2305 answer; it is documented at each call site as the reason, not left for a reader to wonder why the live and offline paths differ.
  - Every other call site (production and test) that does not care about this axis — `routeCannotChangeVerdict`'s `inFlight = []` preview in `Client.fs`, and every existing test in `LanesTests.fs`/`SchedulabilityTests.fs`/`BatchTests.fs`/`RankTests.fs`/`ChoreTests.fs`/`ProtocolTests.fs`/`ScanRoundTripTests.fs`/`CrossRepoRankTests.fs` — passes `Set.empty`, which is a no-op filter and changes none of those tests' asserted behavior (confirmed: full regression suite green before and after, same counts).
- PD-008 [AC-001] complete, ADDED IN REPAIR 1: `addCmd` (`Client.fs`) gains an ADVISORY (non-fatal) warning, printed on stderr in the same style and at the same point as the pre-existing `laneOfOneWarning`, when the ISSUE BODY `add` is about to board already declares a token that exactly names a currently-generated artifact. It does not refuse to board. See PD-009 for why refusal was rejected.
- PD-009 [AC-001] complete, ADDED IN REPAIR 1 — the `addCmd` gap, decided explicitly per the critic's requirement 4: `add` boards a `Paths:` declaration a human or host ALREADY WROTE into the GitHub issue body (via `gh issue create` or a board editor) — there is no `--paths` argument on `add` for PD-002's refusal to intercept, because the declaration to react to already exists before `add` is ever invoked. Two remedies were weighed:
  Remedy A, REJECTED: **refuse to board** (mirror the widen-time hard refusal). The only remedy available to the filer would be to EDIT THE LIVE ISSUE BODY, and an issue-body edit invalidates that item's delivery-route receipt `subjectRevision` (`pnext-item`'s own binding rule, restated by this repair's own coordinator) — trading a silent gap for a strictly more expensive and more disruptive one, and stranding an already-authored issue off every scheduler in the meantime.
  Remedy B, CHOSEN (PD-008): **advisory warning, board anyway.** Matches the existing `laneOfOneWarning` precedent in the same function exactly: a real but non-fatal finding, surfaced immediately rather than discovered later, without blocking the filer or forcing a body edit. `.github#2216` is the measured proof this gap is real and not hypothetical: it is open right now with both `registry/driver-skill-manifest.json` and `registry/coordination-kit-skill-manifest.json` verbatim in its live `Paths:`, filed before either this warning or the widen-time refusal existed.
  This does not reopen AC-1: `.github#2216`'s own generated tokens are cleared from every collision computation by PD-003/PD-007 regardless of how they got into its `Paths:` line (`excludeGenerated`/`schedulable`/`partition` all read the CURRENT declaration, not its history) — PD-009 is about telling the filer their declaration is pointless, not about a live collision it could still cause.

## Performance Intent
No performance intent is declared for this work item — `generatedTokens`/`excludeGenerated` are O(n) set lookups over already-in-memory token lists. CORRECTED IN REPAIR 1: the original claim that the `generatedPathCollector` process invocation is "reused, not duplicated" across call sites was inaccurate as written — `activeCollisions`, `overlapCmd`, `updateTouchSet`, `renderLiveDecision`, and (as of PD-008) `addCmd` each independently invoke it within one command's lifetime, so a single `widen` call, for instance, launches `scripts/generated-paths` more than once. The critic recorded this as a non-material, pre-existing-idiom note (the same pattern `deliveryPathsVerified` already used before this item): the script is local, fast (~40ms per the ADR-0044 roster's own measurement), and each call site's independent resolution is a correctness-neutral cost, not a correctness bug. Left unchanged in this repair; a follow-up MAY cache it per-process if the repeated cost is ever measured to matter.
