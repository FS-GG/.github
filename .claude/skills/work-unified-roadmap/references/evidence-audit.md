# Reconcile a programme roadmap against code

Use this mode for a requested programme audit or restructuring, not every feature or ordinary PR.
Keep the requested repositories and outcomes in scope; a roadmap review does not start its implementation.

## Establish the actual frontier

Fetch or read the current protected defaults and retain exact revisions. Inspect local branches separately:
an existing file may be unmerged, and a local branch may have no remote. Check current owner plans and
accepted artifacts before proposing another implementation or marking an old unchecked row complete.

For each material capability, follow the real path: entry point, producer implementation, contract/tests,
accepted evidence, immutable package, receiver pin, and enabled operation. Stop at the boundary the evidence
actually reaches. Useful distinctions are source-delivered, contract-qualified, published, installed,
provider-accepted and operationally observed; these are report labels, not a new workflow state machine.
A CLI banner is not its dispatch table, a package pin is not activation, and a controlled provider fixture
is not a live representative rehearsal. Preserve unknown or unavailable observations.

Keep sealed historical evidence immutable. A handoff's old pending list can be superseded by newer native
receipts without editing that handoff. Before changing a machine-consumed roadmap, identify revision/digest
bindings and the owning amendment route. Prefer reconciling the human navigation projection when no
execution contract changes. Never pair a new roadmap body with an old accepted digest.

## Make the result executable and readable

Put the current frontier, next acceptance boundary, owner and concrete missing evidence first. Replace stale
current statements instead of only appending another progress paragraph. Retain historical evidence through
immutable links or an explicitly historical section; preserve stable headings that existing links use.
Keep the detailed milestone ledger with its native owner, and avoid a second mutable completion list.

Use a dependency graph when several lanes join. Solid edges should identify real data, artifact or authority
prerequisites; distinguish optional reuse and preparation. Separate source readiness, installed qualification
and effect authority. Name independent work that remains possible during a protected-operation wait, and name
the shared resource/touch-set that requires an integrator or serialized execution. The graph does not grant
permission, allocate staff or authorize extra agents.

Scope a tool refusal to its actual entry point and governing contract before declaring every delivery
route blocked. An alternative must be explicitly sanctioned by the current policy; a successful older
merge or available CLI capability is not authority. Preserve the refused boundary unchanged.

Connect each finding to an evidence link, planning correction and acceptance example. Existing accepted
components should be reused at their proven scope. Do not create a new generic router, executor or replay
implementation merely because its installed consumer is unfinished. Keep package publication, receiver
adoption, clean creation, retained upgrades and default activation separately visible.

Check the final document for contradictory frontier/version/default claims and dangling local/remote links.
Validate mirrored source skills and applicable repository checks. Report merged source guidance separately
from any package publication or installed rollout; changing an installed skill cache alone is not durable.
