# Work Programme

Temporary replacement for `work-unified-roadmap`. The
[Unified Roadmap v3](../../../docs/roadmaps/2026-10-07-unified-development-roadmap-v3.md) open index and existing owner plans remain authoritative.
Start development only on requested advancement; inspection, maintenance and audits retain their own scope.

## Default workflow

Use the user-selected V2-CTX-01 default: pinned packets, typed returns, `delta` views, bounded `view`, declared
mechanical `reuse` and existing check watchers. Use the dependency-free [context helper](references/context.md)
for parent retrieval, safeguard reviews, pinned guard-command preparation and native context reports, including
when CLR helper execution is held. See the [context-efficiency plan](../../../docs/roadmaps/2026-10-05-programme-context-efficiency.md).
Delivered coordination behavior does not establish whole-family savings, remaining integration or effect authority.

For horizon planning, recurring qualification failures or changes to acceptance tooling, read
[delivery reliability](references/delivery-reliability.md). It records the 2026-10-12 review and maps
its findings to these defaults; its historical observations are neither a current frontier nor another
task ledger. Refresh the owning facts before selecting work.

## Delegate recovery before loading history

First check available runtime capacity; a killed parent does not prove its children or operations ended.
When no current handoff exists, bootstrap follows [crash recovery](references/crash-recovery.md) before
selecting work. Missing handoff is a recovery mode, not a reason to wait for a report or start over.

Use one temporary Sol-medium worker with `fork_turns: "none"` for bounded bootstrap. Give it user scope,
known identities/references, actual resource constraints and this skill path. It reads
[bootstrap](references/bootstrap.md), refreshes selected native facts, preserves every active reservation,
and prepares the existing snapshot and packets. It returns a compact decision view and finishes; it makes
no dispatch, ownership transfer or remote effect. Count its capacity and telemetry. Reuse fresh existing
owner artifacts instead when available. If delegation is unavailable, recover locally within the same bounds
and report the limitation.

The parent reads its own governing instructions and the decision view, rather than detailed handoffs,
whole roadmaps or packet bodies. The protected [Unified Roadmap v3](../../../docs/roadmaps/2026-10-07-unified-development-roadmap-v3.md#2-open-work-and-owning-plans),
its named open outcomes and owning plans remain authoritative. The bootstrap worker resolves their relevant sections
and organization-inspection obligations. Fresh-read native admission before parent-owned effects. Preserve
campaign, feature, original/current item and attempt, owner, branch/PR and unknown operations through restart.
Pin the governing skill revision once per selected window; unchanged applicable instructions need no
repeated exposure after an owner confirms receipt. Revalidate after source/scope changes. An index,
snapshot, return, package pin or checkbox cannot establish completion or authority.

Assemblers read [adapter](references/adapter.md); the parent reads it to construct or troubleshoot inputs.
Use one private mode-0700 directory outside checkouts; count helper CLR resources and batch compatible reads.
Recovery preserves original timestamps, unknown reservations and genuine packet/return joins.

Dispatch ready lanes within actual capacity. Integrate or repair the active set before opening more PRs when
the queue limits progress. Hosted admission follows the live runner queue independently of free agent slots;
continue independent local work while hosted work drains. Refresh after material native changes.

Choose the next horizon by the nearest independently useful accepted consumer outcome, not PR count
or available agent slots. Finish the selected publication/install/adoption path while useful disjoint
preparation continues. Use v3 section 1.1 compatible receiver cohorts with separate assertions; routine
process adoption need not await Linux containment, qualified driver correctness need not await a
statistical savings experiment, and WASM-only adoption need not await presentation adoption. Do not
reopen completed Board/Portal work, stopped profiling or unselected conditional scope.

For ordinary advancement, use a narrow ready assertion from an open owning plan, one accountable owner,
and one integrator for shared surfaces. Prepare genuinely disjoint source or receiver work in parallel
within measured resources; a source merge never proves publication or installed use. This is the
existing owner route, with no separate process lane, mandatory cohort, packet form or benefit gate.

## Keep ownership through accepted closure

The parent owns scope, capacity, shared-surface conflicts and exceptional decisions. One accountable
owner per lane carries implementation, tests, evidence, PR updates and routine delivery through accepted
closure in an isolated worktree with an explicit touch-set. Reuse that owner for ordinary milestones and
repairs. Route failed checks using exact native references before reading logs in the parent. Owners diagnose, repair and qualify within their existing
scope, authority and budgets, preserving the first failed attempt. Escalate scope/authority changes,
cross-lane conflicts, unknown effects and root-owned safeguards. Keep mechanical checks and detailed
reconciliation with the owner; return discrepancies, unresolved decisions and evidence pointers instead
of successful hash rows or complete manifests. When delegation is unavailable, run the same checks locally
with bounded result summaries. For safeguards, the owner prepares a
bounded `review` with changed code, explicit proof obligations and mechanically verified unchanged pins;
the parent reads required logic and expands missing obligations rather than importing the entire bundle.

At lane assignment, state the existing user authorization, allowed operations, selected execution profiles,
resource/time bounds, integration owner, acceptance signals and escalation conditions in the existing packet.
Apply [routine-decisions](../routine-decisions/SKILL.md) for typed same-owner preparation, qualification,
repair and observation routing within that boundary. It keeps one current view, unresolved original effects
and a 2KiB changed-decision projection; no per-attempt parent approval is added. Retain native logs and the
first failure. Root reviews milestone semantics/results or changed authority; fresh native prerequisite
checks and operation-specific admission still run.
Delegate routine PR admission and delivery to the lane owner where repository integration is disjoint;
retain one designated integrator for each shared surface. Publication, uncertain external effects and
explicitly root-owned safeguards keep their applicable admission boundary. A return cannot expand authority.

Bootstrap or lane owners assemble `packet` directly from files. The parent receives path/digest, scope,
instruction inventory and omissions, not the body. Deliver governing instructions whole and mandatory to
the responsible worker; the parent reads those governing its own actions. The receiving owner confirms
applicability before acting. Never shorten instructions to fit; plan excerpts/history stay retrievable.

Resolve newest available Astra **high** for new major planning and Sol **medium** for implementation:
currently `gpt-6-astra`/`gpt-6.1-sol`. Spawn with explicit model/effort and `fork_turns: "none"`; report
unavailable routes rather than substitute. Valid plans skip planning; material scope/architecture/dependency
changes need it, while restarts, head changes and failures do not. Respect the v3 open-outcome and
parallelism boundaries; do not split coupled work or pre-plan unselected features. Assemblers/planners read [feature planning](references/feature-planning.md)
when applicable. Implementation packets include [work-roadmap](../work-roadmap/SKILL.md), owner plan,
ready window, branch/PR, authority, acceptance and stop. Reviewers are optional, with exact-source findings.

Packet-bound owners retain `fsgg.programme.lane-return/1` under the
[adapter contract](references/adapter.md#additive-offline-delta-input). Normal messages provide its path,
identity/exact head, changes since the prior return, boundary state, evidence reference and parent action
(or `none`), aiming for at most100 words. Reserve 150–300 words for substantive exceptions. Material detail
stays in the artifact; keep packet, original-attempt, source and return-revision joins truthful. The same owner
repairs malformed returns. Neither a return nor an acknowledgment establishes acceptance.

Consume decision deltas and the complete reservation inventory, retaining unknown/absent owners. Expand
exact evidence only for inconsistencies, architectural joins, user requests or root safeguards. Before each
expansion, name the parent decision or required review obligation and select only the evidence needed to
resolve it. An exception category alone does not justify reading an entire artifact set. Use bounded
`view` and complete mechanical `reuse`; refusals require retrieval/recomputation. Before parent reads,
select fields/ranges and an output bound; redirect raw logs/large responses privately. Truncation is incomplete
evidence: retrieve the missing obligation or route it to the owner. Default parent reads to4KiB of selected
text and8KiB stdout; name the reason and increase the bound only for a concrete obligation. Whole applicable
instructions remain mandatory. Use pinned command descriptors instead of rebuilding long qualification
scripts in conversation; existing guards and fresh admission by the designated owner retain execution authority.
Explicitly root-owned effects still require root admission. Never read binaries as text.

After a repair or review milestone, consolidate the existing current view under
[routine-decisions](../routine-decisions/SKILL.md), with exact source, established outcomes, unresolved
obligations, evidence pointers and next action. Derive reports/handoffs from that view and accepted
outcomes; keep history separate. A current view cannot establish acceptance or erase reservations.
The parent expands history only for a named decision or required review obligation.

For an external blocker, record the exact missing evidence or capability, accountable supplying owner
(or explicitly unknown), first-observed time, affected assertion and reopening condition in the existing
decision view. Repeat discovery only when new evidence or a concrete authentic location could change
the decision. More local harness repairs cannot supply missing provisioner trust, original effect
receipts, candidate custody, engine access or consenting-player feedback. Preserve the hold and advance
independent ready work.

At a completed milestone, consider owner-context rotation when native observations show repeated
compaction or recovery rereads. Follow [context guidance](references/context.md): checkpoint current state,
retain the accountable owner and every original identity/reservation, then use supported fresh-context
continuation. If unsupported, keep the owner and report the gap; never restart an uncertain effect.

## Make acceptance a dependable development capability

Separate development authority from final acceptance. Apply these defaults within the assigned scope:

| Operation | Authority and acceptance boundary |
| --- | --- |
| Edits, builds and focused tests in the approved isolated workspace | Owner executes and repairs within resource limits; no per-attempt parent grant |
| Read-only CI observation and evidence collection | Automatic bounded observation, quota and retention checks; exceptions return to the owner |
| Ordinary PR updates and integration | Designated owner/integrator uses existing admission and required checks; escalate conflicts or scope changes |
| Publication, live-store mutation, privileged/native safeguards | Operation-specific admission, custody and final evidence remain required |
| Uncertain external effects | Observe the original identity and reconcile before retry |

Use edit → incremental compile → focused tests → owner semantic review → full required qualification.
During repair, use relevant cheap checks without rerunning the full suite after every edit. A distinct
reviewer is risk-based and optional for ordinary reversible source work; retain any selected independent
review and protected safeguard. Run the required coherent exact-head PR/native qualification on the final
assembled candidate submitted for acceptance, and rerun applicable required checks for each changed final
head; comprehensive protected parent,
release and installed-receiver boundaries remain additional obligations, never a deferred substitute for
that candidate's checks.
Run the existing compiler early inside the approved environment; normally submit compiling source and
resolved diagnostics for semantic review. After two failures of the same class, sweep the affected module,
expression or generation path and make one coherent repair before another qualification. A cheap parse
check must inspect diagnostics as well as exit status and never replaces compilation or required tests.

Record observed capacity, live and unknown reservations, storage evidence and the first workload peaks
in the existing owner artifact before increasing local concurrency. Follow the
[capacity window and assembled test candidate](references/context.md#capacity-window-and-assembled-test-candidate)
route, including `bash tests/work-programme/run.sh --preflight` for this repository’s maintained suites.

Before expensive qualification, run relevant cheap deterministic checks on the final candidate: input
shape and native identity syntax, branch-specific expected results, generated metadata/digest bindings,
mirror/link consistency and workflow selectors. Inspect the transitive launch closure of each test
command: a Python or shell entry that invokes CLR, native tools or external effects needs that profile
and its admission. A language label is not an execution boundary.

For the selected milestone, exercise the smallest genuine end-to-end acceptance path as early as its
prerequisites and authority permit. Ensure failures yield usable evidence, then add focused regressions
and the broader coverage required for release. Separate component checks do not establish the integrated
journey. Exercise real library/caller control flow with inert external transport where feasible: preserve
callback lifetimes, request/response identity, effective runtime fields and failure/cleanup behavior.
Recorded actual-runtime fixtures supplement adversarial controls; test count alone does not establish
representative integration. Keep candidate package-consumer checks early in the existing preparation
route where admitted; they do not replace required downloaded-only installed proof.

When the real path is blocked, name the dependency and continue useful independent checks;
do not replace real acceptance with a growing surrogate suite or waive release gates.

Use a maintained runner and stable input/result schemas for local tests, native qualification, read-only
remote observation and publication. An operation supplies its command, inputs and a supported profile.
Consolidate the existing canonical execution tooling; do not create a custom launcher, receipt format or
reconciliation procedure for every operation. Preflight actual inputs together, including toolchain identity
versus archive digest, receipt fields, credentials/capability prerequisites and explicit JVM/resource settings.
The runner should own resource accounting, process custody, cleanup, logs, artifacts and terminal results.
Reuse qualified unchanged components; requalify changed behavior and affected joins instead of restarting
an entire qualification campaign for a literal pin or metadata change. Routine PR metadata corrections use
the existing delivery route without a new qualification profile. Required hosted checks remain intact.

Keep freshness checks beside execution. For an authorized operation class, the maintained runner checks
current source/resources, acquires its reservation, establishes the execution deadline and launches in one
bounded transition. Do not send a short-lived grant through conversation before launch; where the current
runner requires sealing, seal and invoke together. Never revive an expired grant or extend an in-flight
operation. Read-only observation may receive a separate fresh budget tied to the original operation;
watch expiry does not imply execution failure, termination or permission to replay an effect.

Where repeated custody or runtime-closure work dominates, evaluate disposable isolated qualification
workers with a proven teardown boundary. Qualify the common platform once per relevant platform change
and verify each operation's changed source, relevant inputs and limits. Prefer a qualified immutable image
with resource enforcement and reliable teardown over repeated full host/toolchain closure checks. Invalidate
cached platform evidence when the image, runner or relevant environment changes; hashes of mutable host
files alone are not an isolation boundary. Privileged fixtures need an environment qualified for their
capabilities. Preserve historical unknown processes and reservations; do not make new isolated workers
inherit their scheduling burden where independence is established. Amortize platform evidence without assuming isolation,
cleanup or runtime equivalence that has not been demonstrated. Extend existing tooling and retire superseded
wrappers; do not introduce a parallel execution framework merely to implement this guidance.

When changes repeatedly cross repositories together, assess the coordination cost and reason for separation.
First prefer qualification against compatible immutable candidate revisions, automated downstream pin
updates and generated progress projections. Where that still dominates delivery, evaluate consolidating
tightly coupled implementation and acceptance code into one repository while retaining useful package
release boundaries. Record the tradeoff and migration implications in the existing owning plan. Repository
consolidation and a new execution platform require the existing material-planning and scope route; this
skill update alone neither performs nor authorizes such migrations.

## Report progress every 30 minutes

While the programme is active, send a user-facing update every 30 minutes, starting at programme
entry. State the reporting window and timezone; cover the interval since the previous update.
Use the existing lane returns and native evidence to report:

- **Completed:** every item completed during the window, its lane and verified outcome. Distinguish
  local preparation, validation, merged PRs, publication and native acceptance; say when none completed.
- **Working on:** each active item, its lane, current stage and what is still needed to finish the
  selected lane outcome. Include an approximate time remaining as a range, with the dependencies
  and assumptions that affect it. If a blocker prevents a credible completion estimate, say so and
  estimate the next useful milestone instead. Refresh estimates from actual progress; do not treat
  an estimate as a deadline, admission or completion claim.
- **Problems:** problems encountered during the window, whether resolved or still open, and any
  remaining blockers, their age from the first observed blocking event, and their effect on progress.
- **User intervention:** state whether intervention is necessary. If needed, name the exact decision,
  information or action required and the affected item/lane; otherwise say none is needed.

Report completed phases and concrete remaining tasks inside open outcomes as well as whole closures.
Do not infer an engineering percentage from binary milestone counts; give a weighted estimate only when
its task denominator and weighting are defensible. Keep updates concise without omitting completed items.
Continue these updates during long-running work and check waits; use existing observations rather than launching reporting-only workers or
interrupting qualification. These updates supplement material progress messages and the final report.

## Preserve integration and effect boundaries

Routine is default. Only explicit recorded human instruction selects heavyweight process for named scope;
labels, registration, modeled work and protected paths/effects do not. Technical checks and effect authority
remain independent; refusals fence affected effects.

The designated integrator (parent or delegated lane owner) admits remote PRs through
`tools/pr-lane-admission.py`: stable campaign/chain, exact pushed head and prepared title/body. Keep one open PR per chain and at most two managed PRs per repository,
including other campaigns. The lock covers participating local callers only. Read the live check queue;
prepare locally when CI limits progress and repair existing PRs. One integrator owns shared-file joins.

For hosted waits use `tools/routine-delivery.py --watch-checks --watch-seconds N` with repo, PR and exact head
(N 1–600). Retain raw records privately; consume material changes or terminal/deadline summaries. Unchanged
polls need no model turn or polling agent. Watchers never deliver and own only direct query children;
count their resources and defer incompatible local qualification. The designated integrator uses the same delivery
helper and [ADR-0084](../../../docs/adr/0084-semantic-reuse-never-cancels-coherent-validation.md) for exact-head
checks, validated reuse, coherent validation, merge and native readback. Never reinterpret pending as disputed,
cancel coherent obligations or accept dependent activation after late failure.

An owner may cancel superseded source-validation jobs only after verifying exact ownership and old PR head,
absence of publication/shared-state effects, and a supported cleanup mechanism. Preserve existing failure
logs, record uncompleted checks as cancelled, and require normal qualification of the replacement head.
This does not cancel ADR-0084 coherent obligations, publishers, migrations, privileged fixtures or jobs with
unknown effects. Observe actual termination/cleanup before releasing conflicting resources; independent
preparation or a replacement push need not wait for unrelated safe jobs to settle.

Prefer release operations bound to an immutable candidate and an explicit publisher revision over a hold
on moving `main`. Reserve the release state and shared surfaces actually mutated; unrelated source work
should proceed when its independence is established. Existing release contracts still govern correspondence,
live authority, original effects and recovery: never substitute new candidate bytes or replay an uncertain send.
For each necessary reservation, record its owner, protected surface, exact release condition and bounded
observation/cleanup route. Automatically transition from terminal watch to evidence readback and release
when supported by qualified tooling and the established condition; do not add a manual handoff by default.
Waiting, cancellation requested or an expired lease alone does not prove safe release.

Make ordinary acceptance cheap and observable: cache immutable journal objects while refreshing live
authority; apply request budgets and quota-aware bounded waiting to ordinary publication as well as recovery.
Within the original bounded terminal observation, attempt logs and available result artifacts independently
for every terminal outcome, including failure and cancellation. Preserve partial evidence and first cause;
artifact/reporting failure must not suppress another available result or renew an expired operation.
Make the first failure diagnosable before temporary resources are cleaned: retain bounded sanitized
stderr/status, actual evaluated fields and expected invariants, relevant runtime/source/artifact identity,
and independent cleanup/reporting outcomes. Exclude credentials, sensitive URLs and full environments.
Do not depend on a later diagnostic PR or invocation to recover values already available to the caller.
The maintained route should automatically collect terminal logs/artifacts, check their identity and produce
one compact result containing the exact candidate, required-check outcomes, artifact verification, cleanup
status and unresolved exceptions. Retain raw evidence; root reviews exceptions and acceptance-determining
assertions instead of duplicating each acquisition and offline check. If original observation expires,
separately budget read-only retrieval of still-retained evidence and record its actual collection time;
never claim timely acquisition retroactively. These are requirements for the existing tooling, not a claim
that every current caller already implements them. Unsupported automation is an explicit owning-tool gap,
not permission to fabricate evidence or add another CLI, receipt ledger or execution framework.

`verify` proves declared byte equality, not authenticity, complete evidence, semantic acceptance, cleanup or
authority. Preserve originals and failed attempts. Reuse installed Execution contracts only where qualified;
keep applicable protected-operation root review, custody, resources, deadlines and one-use requirements;
ordinary development uses the lane-level authority above. Unknown effects require original-
identity observation before retry. Cancel requested is not termination observed. Source, publication,
installed adoption and native acceptance remain separate. Owners cannot admit parent-owned effects by return.

Keep plans in owning repositories and retain v3 owning-plan links and workspace adoption boundaries.
BAR/SC2/FourD product outcomes use the [games roadmap](../../../docs/roadmaps/2026-10-07-games-development-roadmap.md);
shared producers and Game template consolidation remain in v3. When the selected item meets all required
acceptance outcomes, close it in its owning plan with durable evidence and land that closure. Set the
corresponding v3 row to **Done: Yes** only when its whole remaining outcome is accepted; link the closure
evidence and retain the compact row, excluding it from scheduling and recovery. For partial completion,
narrow the remaining outcome with **Done: No**. Land the index in the same `.github` PR or immediate
asynchronous cross-repository follow-up; preparation, source delivery and a completed window alone do
not close the item. Games closures follow their owning index; preserve detailed history in owning plans.
Keep each open-index row compact: current accepted frontier, remaining assertion, entry/blocking join
and owning evidence link. Replace stale current claims after authoritative acceptance; an accepted
migration of one exact store must not remain a task for that store or imply fleet migration. Move
extended completed history to owning reports while preserving links and historical evidence. Report
accepted submilestones inside broad open rows without converting their binary count into a percentage.
Prefer generating and landing projections with the delivery or its automatic immediate follow-up instead
of another manual coordination cycle. Preserve current projection fences where the helper or owning contract
requires them; never mark a pending projection landed to unlock work. Independent implementation and lanes
that do not consume that projection may continue. CI ticks need no projection.
[audit guidance](references/evidence-audit.md) applies to audits, which never dispatch development merely by
editing navigation.

## Diagnose and measure within existing boundaries

The executing owner reads and applies the full
[diagnostic execution policy](https://github.com/FS-GG/.github/blob/main/docs/coordination/diagnostic-execution.md),
including independent failure collection, original budgets, prerequisite fences, custody/cleanup, retained
first cause and separate execution/reporting outcomes. When bugfixes in the same area turn into repeated
small fixes, have the same owner perform a deep sweep of the relevant code before another qualification
attempt. Trace the complete affected paths through callers, shared helpers, guards and tests, including
failure and cleanup paths. Search for the common root cause, duplicated faulty assumptions and sibling
instances of the defect; do not limit the review to the latest failing line or compiler diagnostic.

Use the findings to apply a coherent, more general fix where a shared invariant, abstraction or lifecycle
is responsible. Consolidate connected corrections and remove the cause of recurrence rather than adding
another local workaround. Keep changes evidence-driven and within the affected area; broader review does
not require an unrelated rewrite. Escalate material scope or architecture changes through the existing
planning route. Record the root cause, sweep coverage, connected fixes and remaining uncertainty in the
existing owner artifact, then validate the complete revised path and meaningful regression cases. Preserve
original failures, budgets, custody and admission boundaries. No extra ceremony or runtime/adoption claim
follows from guidance edits.

Use installed `fsgg-coord-engine skill roadmap-telemetry` begin/started/finish and usage-reconcile for native
dispatches/follow-ups, including bootstrap, with bounded best-effort collection. The parent reads
[observation](references/observation.md) before dispatch. Preserve genuine native identities and available
lineage; missing tokens/baselines remain attributed gaps, never fabricated joins. An unavailable collector,
full inbox or incomplete usage attribution must not block otherwise authorized routine development.
Preserve minimal available events in existing private native logs and reconcile detailed usage asynchronously
where authentic joins permit. Block only the affected operation when its correctness depends on telemetry
state; live-store mutation and publication recovery retain their strict boundaries. Record the exact store
identity with schema/status claims. Helper IO/duration never infer model tokens or compaction. Report missing
coverage once and route repair to the existing owner; no new telemetry CLI, service or ledger.

Run `report PRIVATE_ROOT` after a bounded window and the [native context report](references/context.md)
when session records are available. Supply explicit parent/worker sessions, report missing coverage, and
keep session diagnostics separate from authenticated item/dispatch usage. Fix demonstrated refusals and context expansions on the
existing skill branch/PR; charge bootstrap, children, retrieval and repairs to their existing lineage.
Keep model/effort and acceptance stable when comparing context. Track startup/parent-read bytes, bytes per
return and evidence expansions separately from helper IO and whole-family usage where observable. Unknown
measurements remain unknown; a smaller parent or changed guidance alone proves no total savings.
Do not create a separate rollout programme, checkpoint receipts or permanent service.

Before hosted qualification, validate the complete workflow budget, including setup, all required
suites, artifact/report collection and cleanup, against available actual stage timings. Retain variability
and missing-stage uncertainty. A timeout increase may prevent an incomplete run but does not establish
higher throughput. When CI dominates, inspect repeated restore/build work, compatible immutable
artifacts and safely independent stages under the existing
[pipeline preflight](../pipeline-preflight/SKILL.md). Use ADR-0084 exact-head
reuse only with its complete donor and scope proof; retain required checks, coherent obligations and
capacity limits. Do not respond by blindly increasing concurrency or dropping suites.

Use existing native timestamps and owner artifacts for normal progress reporting: accepted outcomes,
material failures or waits, and evidence gaps when relevant. Do not make a prospective cohort, comparison,
new metric, target or telemetry receipt a prerequisite for ordinary delivery. Missing economic evidence
does not waive required acceptance evidence and supports no throughput claim. Keep active lanes focused
on accepted consumer outcomes rather than opening work to fill agent capacity.

Stop at user scope, feature exit or unresolved boundary, distinguishing completed window, delivered feature,
pending publication and blocked work. Retain snapshot/evidence pointers and the bounded dispatch index in
[bootstrap](references/bootstrap.md); future recovery verifies native state rather than rehydrating history.
Close the root observation before returning. Retire this temporary skill/helper when the programme ends or
a qualified successor covers its behavior.
