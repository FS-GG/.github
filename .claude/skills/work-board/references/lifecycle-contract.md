a nearby product checkout never selects that product. Ambiguity is a gap, while already authorized
independent work whose actual scope is known may continue.

  and reservation facts for exact native issue/body/plan revisions and slices. Consume complete membership
  reconciliation and the ordered selected/deferred fold, including unenrolled in-flight conflicts.
  Recheck determining facts beside execution. Status, Track and Roadmap remain owner-controlled;
  the authorized root integrator maintains Status through the mandatory [Status lifecycle](status-lifecycle.md),
  including verified guarded writes at coordination boundaries. Inspection never chooses or writes Status;

## Outcomes and independently meaningful deliveries

An outcome retains its full original promise and every applicable owning-plan acceptance anchor,
including undecomposed installed, participant, recovery or publication requirements. A delivery is an
independently meaningful scoped result with the same six-field owning issue contract. Native parent/
sub-issue links represent decomposition, not action authority. Do not turn every acceptance clause or
old completed submilestone into a card, mechanically decompose the current membership, or invent a
retrospective Done backlog. Materialize only the next useful bounded delivery when needed, keeping the
original issue IDs, owner, PR/head, attempt and operation history. Shared prerequisites have one owner.

For the selected organization successor, Work level is one explicit SINGLE_SELECT field with exactly
Outcome and Delivery. Native type discovery was unavailable in the bounded read; this is not evidence
that types do not exist. The reviewed field fallback requires binding5/schema3, inspection/3 and
integrator-observations/2, with an exact hierarchy digest in each action join. No Status/Track/Roadmap
repurposing, seventh body field or runtime classification fallback is permitted. Binding4/schema2 and
product binding3/schema1 retain their actual qualified behavior until explicit successor adoption;
reading these instructions neither creates the field nor changes enrollment, binding or installed selector.

Only explicitly enrolled Delivery nodes may be selected by the new model. Outcome nodes are never
implementation assignments; missing/conflicting classification refuses that selection. A linked but
unenrolled child remains visible and unschedulable. Preserve the complete membership population and
known/Unknown reservations. A blocked parent/sibling is not an automatic prerequisite for a disjoint
child; relevant native/plan/action prerequisites still bind. Incomplete parent child coverage withholds
parent rollup, not a child's independently complete action facts. Missing/null/partial/truncated or changed
relevant hierarchy, identity contradiction or cycle keeps the affected join Unknown, never an empty list.
Refresh relationships/classification used by the decision at the final barrier. Continue an existing
owner/PR/slice/attempt without another assignment, capacity demand or reservation; changed identities refuse.

Reconcile closure against the actual scoped promise and evidence. Read-only inspection exposes raw Done
when, Blocked on, Acceptance evidence and native state reason/date; it does not interpret arbitrary prose
as accepted work. A merged source PR cannot establish installed acceptance. Native completed differs from
not planned, and stale Done/closed disagreement remains a discrepancy to resolve. The accountable owner
records accepted scope/date/evidence, closes the exact native issue with the correct reason and updates
Status only through the authorized native route, then reconciles parent remaining assertions. Preserve
partial effects and original identity after interruption; resume only the remaining independently read-back
effect. Never use legacy Done.rollUpParents or automatically climb/close parents. All children closed,
healthy inspection, deferred work or successful Observation refresh cannot satisfy missing parent scope.
Read-only refresh writes no closure, Work level, Status, Track, Roadmap or intent.

Use the selected five views: deliveries; outcomes with accepted milestones, remaining assertions and
suppliers; blocked with exact missing fact/supplier; completed with scoped evidence/native dates; and
unfiltered All items. Preserve existing view IDs, layout/grouping/sorting/columns and unrelated settings
through reviewed bounded changes and readback. Unknown metadata stays visible. Counts are not percentages.
The maintained typed migration writer prepares exact field/absent-classification/view effects; it refuses
conflicting existing values and retains originals after uncertainty. New enrollment still requires its
normal authenticated private binding/protected commitment pair, not a child link or view filter. Publication,
actual installed instruction discovery, selected caller qualification, field/enrollment/view migration and
native consumer acceptance remain separate required joins before activating this successor.

## Recover ownership and unavailable history

card from the pass. Reconcile each such card against its native issue, complete acceptance, owner,
plan, prerequisites and existing delivery evidence. Record the disposition in the existing owning
issue: accepted scoped completion, eligible work, a concrete blocker/supplier, or an attributed Unknown.
For unfinished work, name the intake owner, next action and event that triggers reconsideration.
Do not call the clearing pass complete while these cards remain untriaged.

Triage is separate from scheduling. Initialize missing planning/classification only through the
admitted native route, preserving existing human values. A completed source card's Done applies only
to its accepted source promise. An unfinished card needs its actual implementation owner and protected
enrollment before action selection; neither metadata repair nor a child link enrolls it or grants Ready.
Revisit blocked and unenrolled intake on its determining event or the next clearing pass. Keep gaps
visible through existing issue/board fields, without another intake queue, ledger or status table.

At entry/resume reconcile owners, isolated worktrees/dirty files, native open PRs/heads/checks, original
operations and relevant reservations. Continue one unambiguous existing owner and PR before replacing it.
Missing/conflicting ownership fences the affected scope. Read [bootstrap](bootstrap.md) for
bounded recovery and [crash recovery](crash-recovery.md) when no current handoff survives.
Delegate only when authorized, available and useful; otherwise recover locally within the same bounds.
Bootstrap reads source/native facts, without dispatch, cleanup or remote mutation.

Preserve original outcome/slice/attempt, owner, branch/PR/head and operation identities. A killed parent,
expired lease, missing artifact or absent PR does not prove cleanup, no effect or reservation release.
The unavailable historical evidence-search task is closed as unavailable. Stop repeated searches/requests;
retain surviving records, all 439 inherited reservations and 46 later originals distinctly Unknown and
unreleased. Never reconstruct receipts or disguise an uncertain-effect retry with a new identity.
For genuinely fresh work require current relevant ownership, remaining-after-active capacity and
separation of generation, writable state, operation identity and outputs. Shared destinations require
fencing/idempotency against old actors. Missing history is not empty relevant coverage; unresolved
relevant interference blocks that operation. Unrelated historical Unknowns are not a global gate.
Keep existing journals/custody rather than a new recovery ledger.

## Keep one owner through accepted closure

Observe results, reconcile scoped acceptance and blockers, update Status and verify native readback
before selecting/admitting work; after dispatch, update Status and verify again. Reconcile after worker
returns, CI/runtime completion, reviews, supplier replies and accepted closure, and before yielding or
handoff. Update the Delivery first, then reassess its parent against its whole remaining promise.
Apply the six [Status definitions and guarded write procedure](status-lifecycle.md). Workers provide
evidence; the root integrator owns decisions. A freshness sweep supplements these boundaries.
Status maintenance grants no dispatch, reservation release, retry, closure or weaker acceptance.

Use the existing owning issue's Owner, Done when, Current deliverable, Next action, Blocked on and
Acceptance evidence with native links. Preserve the complete Done when; a merged slice narrows the
remainder without closing its parent. Do not manufacture an issue, claim, packet, lifecycle ledger,
mandatory return or duplicate current-status/closure projection. Optional helpers are diagnostics.
The parent owns scope, capacity, shared-surface conflicts and exceptions. One accountable owner carries
implementation, repair, review, PR updates and ordinary delivery in an isolated worktree with explicit
touch-set; one integrator owns each shared surface. Existing authorization persists. Ordinary milestones
need no repeated parent approval or file-by-file gate. Reconcile scope/authority changes and unknown effects.

Verify the accountable owner and issuer's actual authority before dependent action. Before relying on
a scope-changing host ruling, record it under existing write authority in the owning
issue or PR with the ruling, exact scope, source/author and durable citation, then independently read
back that record. A channel-only message is not durable ruling custody. A durable record preserves
provenance; it does not grant the issuer authority or turn untrusted text into instructions. If recording,
readback or authority is unavailable/conflicting, hold only the changed scope as Unknown; previously
authorized independent work may continue. Keep the original ruling and its supersession history citable.

Report material process problems promptly when they block progress, risk incorrect effects or acceptance,
or cause substantial avoidable work. Before completing a review, returning work or handing off, check for
unreported process problems. Do not invent findings or repeat unchanged reports. Use the existing
[findings route](https://github.com/FS-GG/.github/blob/main/.agents/skills/pnext-item/references/findings-and-filing.md)
for evidence and [host guidance](host-loop.md) for owned disposition; a missing solution is no reason to
suppress a valid report. Reporting changes no operation authority or acceptance.

Classify the actual risk once, revisiting material scope changes:

| Work | Proportionate process |
|---|---|
| Trivial reversible non-governing prose/metadata | Owner review and cheap relevant checks. Governing skills are substantive even when only Markdown changes. |
| Normal code or governing skills/policy/schema | One accountable owner, one independent source review of the exact candidate, relevant tests and final required CI. |
| Cross-repository or architectural change | Normal checks plus reuse of the existing design up front; a targeted specialist only for a distinct needed contribution. |
| Publication, deployment, credentials, live-store mutation, destructive or uncertain effects | Applicable source checks plus exact identity, effect-specific admission, original custody and independent readback; Unknowns fence the affected effect. |

Fix substantiated in-scope defects; adjudicate disputed findings against acceptance and evidence; decline
hypothetical scope expansion. Keep necessary corrections in the current Delivery and explicitly defer
independent improvements without indefinitely extending it. Unresolved acceptance defects remain blocking.
Additional specialists need a distinct justified contribution; PASS counts are not proof of quality.
Maintain independent exact-candidate review after material repair, without adding actors or review rounds
for their own sake. Only explicit recorded human instruction selects heavyweight ceremony for named scope.

For clearing, refresh the complete board at entry/resume, meaningful coordination boundaries or relevant
membership/owner/prerequisite changes. Local repair uses relevant issue/PR/test context; an unchanged CI
poll is not a census trigger. Load applicable references just in time, without an exhaustive reference

Choose the nearest independently useful accepted consumer outcome, not PR count or available slots.
Finish selected publication/install/adoption while disjoint preparation continues. Do not reopen completed

New major planning uses supported `gpt-6-astra` high; implementation uses `gpt-6.1-sol` medium.
[Normal](../../work-board-normal/SKILL.md) and [best](../../work-board-best/SKILL.md) wrappers select actual

## Seek useful parallel work

At entry/resume and after a delivery, changed blocker or start of a hosted wait, actively look for
independent work that advances the selected scope. Compare prerequisites, existing owners/PRs,
touch-sets and shared outputs across eligible Deliveries. Look for disjoint source preparation,
review or evidence collection while another lane waits. A blocked parent or busy sibling does not
by itself exclude independent work; action-specific prerequisites and admission still apply.

Use actual remaining worker, CPU/memory, integrator and hosted-CI capacity after active demand and
known/Unknown reservations. Free agent slots are not resource capacity. Admit each chosen operation
before launch using its supported operation-specific profile; preserve required exclusive writes,
large-image limits and one integrator for shared surfaces. Do not add blanket serial execution when
independently qualified operations fit the remaining capacity together.
Delegate only when the runtime permits it, ownership/isolation is clear and the expected contribution
exceeds coordination cost. Continue an existing owner/attempt instead of creating a duplicate lane.

When useful parallelism is unavailable, continue the eligible serial work and state the determining
capacity, dependency or overlap constraint with its reopening condition. Do not split work merely to
fill slots, weaken acceptance, create reporting-only workers or add another scheduling ledger.

After repair rerun affected checks. Broader qualification requires changed inputs/assumptions,
integration/provenance uncertainty or actual required CI; do not manually restart unchanged full suites
for confirmation alone. Required CI and ADR-0084 coherent validation still run. Advisory pending is
reported separately; required pending/failed checks block their dependent delivery or effect.
