# Complete the selected Delivery

One accountable owner carries implementation, verification, repair, review and permitted delivery through
acceptance. Under [work-board](https://github.com/FS-GG/.github/blob/main/.agents/skills/work-board/SKILL.md), read the native issue's complete Done when and owning plan,
including publication, installed, participant and recovery obligations. Follow the common **Normal execution**
section of the [lifecycle contract](https://github.com/FS-GG/.github/blob/main/.agents/skills/work-board/references/lifecycle-contract.md). Ordinary isolated checks
need no Root runtime approval; covered successful steps need no repeated phase approval. Changed scope,
authority, uncertain effects or exhausted bounds return for reconciliation.

## Choose the route before lifecycle work

Use the routine route by default. Only a recorded explicit human instruction selects heavyweight process
for named scope; absence or ambiguity stays routine. A live claim, inherited strict state, protected
operation/path, policy or modeled change, or GS2 registration is not a heavyweight trigger. Preserve its
substantive safeguards. Invalid or unknown technical or operation authorization blocks the affected effect.
A routine refusal blocks the affected delivery until repaired; it does not select heavyweight process
or authorize weakening or bypassing a gate.

1. Keep one accountable owner at a time and one continuous PR. Recover the native Delivery, worktree and
   PR/head. If exactly one open routine PR owns the item, verify its scope and current head, adopt that
   branch, and continue the same PR; never open a second PR because a board projection lagged or an owner
   disappeared. Recover an unambiguous existing branch before opening its PR. Multiple or ambiguous
   candidate PRs refuse routine admission. Genuinely fresh work starts from the current default branch with
   one fresh `routine/<item-slug>` branch and one PR. The coordinator retains intake and Status decisions; workers
   supply evidence rather than creating claims, identities, ledgers or mandatory return packets.
2. Implement the admitted promise in the isolated worktree, within the stated resource share. At meaningful

   failures inspect relevant callers, failure and cleanup paths before coherent repair. Split independent
   concerns into separately reviewable PRs under the existing one-chain/two-managed-PR limits; retain one
   continuous PR for the current slice.
3. Request review without known-red required gates, except explicitly named inherited main failures.
   Keep the PR draft until required gates pass. Use the canonical creation
   and delivery helpers from the [exact-source route](https://github.com/FS-GG/.github/blob/main/.agents/skills/work-board/references/lifecycle-contract.md#qualify-the-actual-path-and-deliver-exact-source).
   A moved head must be reviewed and rebound. The body has exactly one

Telemetry and Observation projection are best-effort, asynchronous observations and cannot invalidate the
merge. They do not replace mandatory native reconciliation and effect safeguards. The routine route adds
no lifecycle ledger, receipt family, review actor or projection PR.

The routine route ends here. Do not execute the lifecycle, identity, claim, critique, receipt, feedback,
or done-stamp instructions in the linked strict protocol for a routine item.

## Owner self-check before review

Before requesting review of a governing or code change, probe the actual failure boundaries. This is
owner work, not another critic or report; inert prose needs none of it.

- **Range:** fuzz or property-test across the full range the API accepts, not only typical values.
- **Partial failure:** for each multi-step write or effect, ask what happens on failure or kill between steps, and test it.
- **Planted bugs:** disable each safety check or guard in turn and confirm a test fails.
- **Reviewer probes:** when repairing after review, re-run all of the reviewer's probes on the new head and add their classes to your tests.
- **Cross-cutting defects** (sizing, concurrency, lifecycle): write the invariant first, then the code, not point fixes.
