# Clear the Coordination board

Use [$atlas](../atlas/SKILL.md) first, then apply the complete canonical
[$work-board](../work-board/SKILL.md) workflow and its
[lifecycle contract](../work-board/references/lifecycle-contract.md).
This entrypoint selects **FS-GG organization Project 3**, including complete unfiltered All items;
do not ask which board, infer a product scope, or schedule from a filtered Ready view.
Use its authenticated qualified installed caller, current protected enrollment and native owning
issues. This skill specializes coordination and persistence; it introduces no second scheduler,
binding, enrollment route or operation authority.

Inherit the canonical work-board Status lifecycle at every result, selection, dispatch and handoff
boundary. Reconcile each Delivery before its parent Outcome; maintain Status with guarded native
writes and verified readback. A read-only inspection or periodic sweep cannot replace those updates.
Inherit canonical proactive process-problem reporting and [owned disposition](../work-board/references/host-loop.md#own-process-findings-and-disposition)
at the existing execution, review, return and handoff boundaries.

The objective is accepted completion of every item in that scope. Recover existing owners,
worktrees, PRs, attempts, pending replies and original effects before selecting work. Preserve each
Outcome's whole promise, including publication, installed adoption and recovery. Execute enrolled
Deliveries through [$pnext-item](../pnext-item/SKILL.md); decompose Outcomes only through canonical
intake and the admitted membership route. A merged PR or a worker's return is a coordination boundary:
read back acceptance, reconcile the parent and immediately return to selection.

## File the Delivery before dispatch

No dispatch without its native Delivery issue, linked as a sub-issue under its Outcome and carrying
owner, Done when, Work level, Track, Status and `Refs` only; the PR `Refs` that Delivery. Shaping an
Outcome files its remaining acceptance as open Deliveries, and all sub-issues closed never means
Outcome done. Enroll each pass's new Deliveries in one batch through the #4941 planner once the
250-row cap is installed, and keep project auto-add of sub-issues off. See the
[rules](../work-board/references/lifecycle-contract.md#file-the-delivery-issue-at-dispatch).

## Keep useful work moving in parallel

An execution invocation authorizes useful subagent delegation within the selected scope and the
runtime's permissions. Actively seek parallel work at entry, after delivery or a changed blocker,
and whenever a lane starts a build, review, CI or supplier wait. Prefer keeping independent,
meaningful Deliveries moving together when their actual capacity and prerequisites permit it.

- Compare the complete eligible work against active owners, exact PR heads, touch-sets, shared
  outputs and remaining worker, CPU/memory, integrator and hosted-CI capacity. Preserve relevant
  known and Unknown reservations. Account each launch before considering the next; free agent
  slots alone establish no capacity.
- Prefer finishing owned acceptance and shared prerequisites that unblock several items. Look
  across repositories and within an existing Delivery for useful disjoint source preparation,
  independent review, receiver preparation or evidence work while expensive execution waits.
  A blocked parent or sibling does not automatically block an independent child. Reconsider
  older deferred product work rather than repeatedly selecting convenient small changes.
- Delegate bounded Deliveries to accountable owners with the full acceptance, existing identity,
  actual source/PR, touch-set, applicable instructions and completion boundary. Preserve an
  unambiguous existing owner/branch/PR instead of starting a competing assignment. Use isolated
  worktrees and one integrator per shared surface under
  [parallel-work guidance](../intra-repo-parallel-work/SKILL.md).
- Use the canonical supported runtime/model route, or an explicitly selected normal/best route.
  Do not create fixed waves, a worker per checklist step, reporting-only workers, extra review
  chains or PRs merely to fill slots. If delegation is unavailable, continue eligible serial work.
- Integrate returned work promptly, resolve overlap, repair substantiated defects on the same PR,
  and preserve independent review and exact-head required CI. Keep finding the next useful action
  while hosted work drains; observe necessary waits through their admitted bounded windows.

## Own and reduce blockers

Treat a blocker as a question about the next action, its supplier and the smallest useful result.
Fresh-read the determining source and native facts before carrying an old hold forward. Pursue
prerequisite work, ownership recovery, supported tooling setup and isolated environment repair that
are already authorized. Missing tools, a poisoned shared cache or an unassembled runtime are not
automatically external dependencies: check the supported installation/preflight route, preserve the
first failure, isolate outputs and continue when the exact contract and resource admission permit it.
Do not invent a new runtime profile, replace credential/license authority or retry uncertain effects.

When another owner must supply a fact or operation, use the existing owning issue/request and
[cross-repository route](../cross-repo-coordination/SKILL.md). Make the concrete request when
authorized; retain its owner, exact missing result, response/observation deadline and reopening
condition. Continue other useful work while waiting. Source preparation can advance while later
publication or receiver effects remain held; scoped Unknowns do not become a global stop.

Keep Owner, complete Done when, Current deliverable, Next action, Blocked on and Acceptance evidence
in the existing owning issue. Report changed deliverables, blockers and decisions concisely, using
native evidence rather than a duplicate status table. Capture reusable findings through Atlas;
keep logs, runtime assets and private custody outside it.

## Finish only on accepted scope

Before declaring success, reconcile current unfiltered membership, native completion reasons,
owning-plan acceptance and every remaining parent assertion. Every item must have its actual scoped
acceptance established; neither Status Done, all children closed, healthy inspection, a source merge
nor an empty Ready view proves board completion. Do not weaken promises, remove blocked cards or
close required work as not planned to manufacture completion.

Do not end merely because one lane finished, the initial shortlist is exhausted, CI is pending or
all currently considered lanes look blocked. Reconsider the whole scope, suppliers and useful
parallel or serial preparation first. If only genuine external dependencies remain after complete
intake reconciliation, identify each held slice, supplier and reopening condition in native issues.
Continue an owned reply/job through its admitted observation window; do not poll unchanged holds
with model turns or run an indefinite watcher. A forced external hold or runtime limit is an
**incomplete handoff**, never successful board completion. Preserve durable native/Atlas restart
pointers and state whether an actual monitor remains running; returning implies none.

A user stop/cancel immediately stops new selection. Retire owned work through
[$stop-with-handoff](../stop-with-handoff/SKILL.md) and resume through
[$continue-from-handoff](../continue-from-handoff/SKILL.md), retaining original effects and identities.
