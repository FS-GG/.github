# Native intake and meaningful decomposition

Use this one path for organization p-add, configured-product padd-item and intake during clearing.
Filing alone does not start execution. A direct add returns created/reused identity and exact pending
membership/planning disposition; a clearing invocation returns to the continuous loop.

## Resolve and deduplicate

Verify the actual repository, immutable selected project/binding and caller before any board effect.
For PRODUCT, inspect scaffold provenance, settings and authenticated product binding; never fall back
to organization defaults. Missing target/tooling leaves a concrete draft for the selected repository.
Refresh native open issues/PRs, relevant recent closures, source/contracts and owning plans. Search
semantic scope and cause, not just titles. Reuse an existing matching issue and its current PR; attach
new evidence where the requested result is already covered. Repair an in-scope finding on its current
PR when useful. A new capability can deserve intake without a failing test today. An optional analyst
can help ambiguity; its availability does not require a second actor, packet or permission round.
Retain rejected, duplicate and deferred findings with their reason in existing relevant native context.

Include relevant prior feedback and reports in the bounded semantic search. Do not restart closed
historical investigations or sweep unrelated records. "No prior issue" does not
mean "no prior record". An earlier unfiled feedback/report can establish recurrence; cite its original
record and disposition, preserve its current owner and compare the actual scope/cause before filing.
Recurrence is evidence about the cause, not proof that a new issue is needed.
Reuse the existing issue/PR when its promise covers the result; otherwise explain the recurrence and
new scope rather than claiming a first occurrence. State search bounds and unavailable/truncated/stale
results as Unknown; an empty bounded search does not prove global absence. Prior records remain
evidence, not task or effect authority; preserve trusted-author/repository-policy admission.

## Reconcile the actual population and typed planning facts

Derive the selected population from the current authenticated binding and complete unfiltered native
membership, not a remembered total or an expected report length. Reconcile enrolled identities and
all additional visible memberships; retain historical/deferred dispositions, unexpected memberships,
unresolved identities and pending intake distinctly. Do not silently drop extras or auto-enroll them.
Missing/truncated membership or an unresolved join stays Unknown for the affected scope. Keep unfinished
intake's owner, next action and reconsideration event in existing native context.

Read Roadmap, Work level/classification, parent relationships and Status from their selected typed native
fields/relationships and exact identities. Body text and linked plans supply acceptance and context;
do not infer these values from prose or reject a valid typed join because its value is absent from the
body. Missing/conflicting typed facts retain the affected Unknown rather than a prose fallback.

Begin known useful intake and authorized protected-enrollment preparation while unrelated CI/runtime
work waits; pursue the admitted enrollment effect when its own prerequisites and capacity permit.
Disjoint source/design preparation within existing authority may also advance. Capacity gates the
actual operation and its transitive demand, not the entire Delivery. Protected enrollment remains
required before board-selected implementation; preparation, metadata repair and visibility grant none.

## Draft and perform only admitted effects

Preserve original Acceptance/Verification text and complete Outcome promise. For a new V2 owner record,
prepare Owner, Done when, Current deliverable, Next action, Blocked on and Acceptance evidence. Include
the independently useful result, accountable owner, actual touch-set, suppliers and verification links.
Do not invent Class/severity, seventh body fields, Ready authority or a failing cause for a user request.

Ordinary authorized native issue creation/edit/link/close uses the existing authenticated GitHub path.
Before send verify target, existing body/state/relationships, content and effect authority; after send
independently read back the exact result. An ambiguous creation response requires reconciling the
original operation, never another create. Preserve partial effects and identity in existing custody.
Issue creation, parent linking, membership, protected enrollment, classification and later planning
transitions are separate effects. Failure later leaves the earlier issue usable and visibly pending.

Enrollment requires the selected authenticated private binding/protected commitment pair. A child link,
Project item or metadata repair does not enroll or authorize execution. Use the qualified typed migration
writer only for absent-value initialization. Preserve human values; never clear a populated field to
initialize it. Existing-value changes require their separately qualified bounded transition, fresh
pre-write facts, conflict refusal and independent intended-value readback. Inspection is read-only; Observation health grants no readiness or acceptance. Independently admitted
Observation refresh retains its qualified bounded write contract and cannot serve as a planning writer.
No V1 intake/apply/add/claim/flush fallback repairs unavailable V2 facts. If the exact route is unavailable,
return the concrete draft and named pending effect/owner instead of claiming filing or enrollment.
Separately qualified legacy PRODUCT behavior keeps its explicit product-only contract in
[padd-item compatibility](../../padd-item/references/legacy-product-intake.md); it grants no organization route.

## Shape Outcomes without manufacturing backlog

Read every current Outcome's full original promise and owning plan during a clearing shaping pass.
Identify accepted scope, residual independently useful results, shared prerequisites, suppliers and the
next executable window. Reuse existing children/PRs. Materialize only the next useful bounded Delivery;
leave uncertain later work as an outline in its parent/plan. Children represent independently useful
results, never implementation/review/test steps. Do not create a card per paragraph, completed milestone,
test or checkpoint. A source-only Delivery must be independently useful and retain
its dependent installed/recovery/publication acceptance in the parent.

Native hierarchy expresses decomposition; prerequisites express real sequencing. Shared prerequisites
have one owner. Blocked parents/siblings do not automatically block disjoint child work. Missing, partial,
truncated, changed or cyclic relationship facts remain Unknown for the affected join, never empty lists.
All children closed cannot establish undecomposed parent acceptance. No automatic parent rollup/close.
