## Observed

`independent-review.md`'s **Gate-inversion evidence** section is six numbered steps that are all about
whether a gate *can* fire: invert it by breaking its subject, don't accept predicate inversion, make
sure the test that claims a property provides it, make the fixture reproduce production, don't measure
in an environment that supplies what production lacks.

**Every one of those steps presupposes that the gate runs.** Nothing in the section requires showing
that the automation which is supposed to invoke the gate actually invokes it. A critic can follow all
six steps faithfully, grade a gate `JUSTIFIED`, and be entirely correct — about a gate CI never
executes.

**This is not hypothetical; the live instance is on this board.** `.github#2537` is exactly it:
`.github#2417`'s critic-succession gate-inversion fixture *is invoked by no workflow*. The proof that
succession's refusals can fire has never run in CI. Inverting that fixture by hand reds it, which is
what step 2 asks for and which would certify it `JUSTIFIED` — while the CI signal it exists to produce
has never once been generated.

## The second, narrower gap: vacuous green

Step 2 says to break the subject and run the suite. It does not name the case where a gate passes green
because its **input set is empty**. Measured today in `.github#2534`'s lane: of seven gate mutations,
the most load-bearing was the one that **emptied the scanned corpus** — the offenders leg then passed
*vacuously green*, and only a separate non-vacuity leg caught it.

The lane's own conclusion is the rule worth writing down: **a source-text gate has this failure mode and
a behavioural one does not.** That is why that item's scanner self-tests *call* `Ordering.scan` rather
than grep for its name. A gate whose subject is source text can be satisfied by an empty corpus in a way
a gate that executes the code cannot.

## Why the contract, and not another worker brief

The host hand-wrote both rules into **every** worker brief this session, because the pattern kept
recurring across independent lanes on unrelated items:

- `.github#2510` — root discovery tested the DECLARED root list before filtering to directories that
  exist, so every declared root vanishing left the scan iterating zero files and the gate exited 0

- `.github#2534` — mutation #4 above.

Four independent lanes in one session. A rule the host must restate in every dispatch is a rule that
belongs in the contract; `.github#1610` and `.github#2223` are the precedent for what happens when this
class is found and nothing generalises from it — `#2223` measured ten instances across six items and
four repositories three months after `#1610` found the same shape.

## A gate keyed on PATHS is not merely accidentally right — it is SELECTIVELY silent

Measured on 2026-08-14 while `.github#2230` was being implemented, and this is the sharpest form of the
class in this row.

`.github#2510`'s `tests/skill-quality/agent-definition-coverage.py` caught a real, serious defect —
`#2230` would have emptied `.claude/agents/` and silently renamed every documented dispatch. But it
caught it **by accident twice over**:

1. It asserts a **directory's existence**, not a successful dispatch. A gate that tested resolution
   would have caught it on purpose.
2. It runs under `skill-quality.yml`, whose `on: pull_request: paths:` filter is host-verified to
   include `.claude/agents/**`, `.claude/skills/**`, `.agents/skills/**` and the registry — and **not**
   `plugins/**`, `.claude-plugin/**`, or `.claude/settings.json`.

`#2230`'s implementation happened to **delete** files under a watched glob, so the trigger fired. **The
"keep both homes" variant — add the plugin, leave `.claude/agents/` populated — would have touched no
path in that filter at all.** The gate would never have run, and two disagreeing copies of the route
definitions would have landed with nothing watching.

That variant is not hypothetical: it is the one a reasonable implementer picks *to stay green*, and it
is the `.github#485` / `.github#865` two-copies-disagree shape this org files most.

**So a path-filtered gate is quietest on exactly the variants that keep the old artifact in place** —
the additive, apparently-safe changes — and loudest on the destructive ones that are easiest to notice
anyway. Inverting such a gate by hand proves nothing about whether CI will ever run it for the change
that matters.

## Acceptance criteria

1. The gate-inversion section requires establishing that each inventoried gate is **reached by the
   automation meant to run it** — named workflow, job, and invocation path — not merely that it can be
   made to fail when run by hand. A gate that no workflow invokes is graded `NOT_MEASURED` at best, and
   is a material finding by the same logic step 3 already applies to a surviving inversion.

   **"Reached" includes the trigger's own path filter, evaluated against THIS change.** Where a gate
   runs under a `paths:`-filtered workflow, the evidence must name the filter and show the change
   touches it. A gate that is wired, invertible, and simply never triggered for the diff in hand is
   indistinguishable from an absent one — and per the section above, it is quietest on precisely the
   additive variants that leave a stale artifact in place.
2. The section names **vacuous green** explicitly: a gate that passes because its corpus, fixture set,
   or input collection is empty. Where a gate's subject is source text, a non-vacuity leg is required —
   the gate must be shown to go red on a non-empty corpus containing a genuine offender, so that
   "found nothing" is distinguishable from "looked at nothing".
3. The distinction the `#2534` lane drew is stated in the contract's own words: a source-text gate has
   the vacuous-green failure mode and a behavioural gate does not, so a self-test for a scanner should
   **call** the scanner rather than grep for its name.
4. The addition lands in the AUTHORED prose of `independent-review.md`, below the generated
   `fsgg-protocol:review-policy` block (which ends at line 18) — it is not a change to the generated
   projection, and the generated block must remain byte-identical.
5. `.github#2537` is cross-referenced as the worked instance rather than restated, and this row does not
   duplicate or pre-empt that item's own fix.
6. The section does not grow a seventh open-ended "be thorough" step. Both additions attach to the
   existing numbered steps as bounded, checkable requirements, preserving the section's stated bound
   that inversion is one mutation per touched gate and must not become a suite-wide sweep.
