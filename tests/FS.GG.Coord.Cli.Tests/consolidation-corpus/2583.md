## Observed

The delivery-route receipt binds to a hash of the issue **body**. So **editing a row's body to fold
another row's cause into it stales that row's receipt and removes it from the schedulable set**, while
**minting a brand-new row costs nothing.** The board's freshness mechanism prices consolidation above
filing, in the direction that grows the board.

*Verification, this checkout at `cb33188c`:*

- `src/FS.GG.Coord.Cli/Client.fs:458` — `deliveryRouteRevision body = hashHex (deliveryRouteSubject body)`.
- `src/FS.GG.Coord.Cli/Client.fs:448-453` — `deliveryRouteSubject` drops only volatile declaration
  lines and blank lines; **every other body line is in the hash.**
- `src/FS.GG.Coord.Core/DeliveryRoute.fs:94` — `if receipt.SubjectRevision <> expectedRevision then
  yield "subjectRevision is stale"`.
- `src/FS.GG.Coord.Core/Schedulability.fs:146-148` — `DeliveryRoute.Stale` maps to

- Measured live: `scripts/fsgg-coord delivery-route show .github#1858 --json` →
  `malformed response reading FS-GG/.github#1858: subjectRevision is stale. That is a FAILED READ`.

**Measured the other way, on this same board tonight:** a **title** edit does not stale a receipt.
`.github#2555` was retitled and `delivery-route show .github#2555 --json` returned `kind: "current"`
immediately after. Titles and comments are outside the hash; bodies are inside it.

## Root cause

`.github#2392` narrowed this hash **deliberately and correctly**. It excluded `Paths:`, `Class:`,
`Blocked on:` and `Blocked by:` precisely because the protocol's own commands rewrite those lines, and
a receipt that a required protocol action invalidates is a receipt that fails for doing the right
thing. **That reasoning is sound and this row does not propose reversing it.** Its own comment at
`Client.fs:440-447` is explicit that distinguishing a scope-growing edit from a neutral one needs a
semantic comparison it declared out of scope.

**This row is that out-of-scope remainder, and the fix is not "hash less."** Hashing less would make a
genuine scope change invisible, which is the property the receipt exists to provide. What is missing is
a way to tell a **consolidating edit** — transplanting another row's evidence and cause into this row,
which strictly *adds* context and never redefines the work — from a **scope change**, which redefines
what was judged and must re-open the route decision.

## Why it matters now, with the number

The board grew **net +12 in 24h** while 25 items landed. Analysis of the 27 open rows found **no true
duplicates** — every one carries a `## Dedupe` section naming the searches performed. The board did not
grow from careless filing; it grew because **filing is the cheap operation and folding is the taxed
one.**

The consequence is already visible in the record. `.github#2381` carries four separate evidence
transplants recorded as **comments**, each explicitly saying it is not a new row — and `#2381` has
**no delivery-route receipt at all**, which is the only reason comment-transplanting worked there
without cost. A row that *does* hold a current receipt cannot be consolidated into without
de-scheduling it and requiring a fresh route decision.

This is upstream of any filing-bar guidance: **a bar that instructs an agent to fold, applied to a
board that taxes folding, will lose.** The whole consolidation pass on 2026-08-14 was therefore
conducted through comments and title edits only, and said so on every row it touched — correct under
today's mechanics, but it means corrections live in comments rather than in the body a future reader
reads first.

## Acceptance criteria

1. A body edit that **only adds** content — no change to any existing non-volatile line — does not
   stale an otherwise-current receipt. Establish the rule on the receipt's own terms: state what makes
   an edit route-neutral, rather than special-casing an append.
2. An edit that **modifies or removes** existing body content still stales the receipt. Demonstrate
   both directions; a rule that only ever answers "still current" has measured nothing.
3. `.github#2392`'s volatile-line exclusion and its legacy read-side migration bridge
   (`legacyDeliveryRouteRevision`, `Client.fs:461-468`) are preserved unchanged. This row is additive to
   that fix and must not regress its AC5 guarantee.
4. **Gate-inversion evidence, per `.github#2551`:** the new leg is shown to go red when the
   additive-edit rule is removed, on a **non-empty** corpus — a fixture whose body set is empty passes
   this vacuously and proves nothing.
5. State the answer for a **comment** explicitly, even though comments are outside the hash today, so
   the next reader does not have to re-derive it from `deliveryRouteSubject`'s line filter.
