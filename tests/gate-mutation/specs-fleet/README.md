# The fleet corpus — mutation legs for gates that live in OTHER repositories

`specs.yml` beside this directory is the `.github` corpus: `scripts/gate-mutate.py` runs it with no
arguments, against this repo, and `#1810`/`#1829` built it. **This directory is everything else.**

`#1830` adjudicated the five never-red gates outside `.github`. Two of them are adjudicable by
mutation, and their legs are here — one file per repository, because a spec file's `target` and
`anchor.produced_by` are resolved against a single `--root` and a leg for another repo would report
`NOT_MEASURED — mutation target … does not exist` in a `.github` sweep, turning this repo's clean
`exit 0` into a `3`.

## Running one

**In a throwaway clone. Never in a checkout of that repo's `main`.** These legs delete and rebuild a
directory; the harness restores it, but `#1830`'s constraint is that a visiting worker does not mutate
somebody else's working tree to make a measurement stick.

```bash
git clone --depth 1 https://github.com/FS-GG/FS.GG.Rendering.git /tmp/adj/FS.GG.Rendering
cd /tmp/adj/FS.GG.Rendering
bash scripts/skill-view generate --source .claude/skills --roots ".agents/skills"   # SEE BELOW
cd -
scripts/gate-mutate.py --root /tmp/adj/FS.GG.Rendering \
    --specs "$PWD/tests/gate-mutation/specs-fleet/FS.GG.Rendering.yml"
```

## THE GENERATE RUNS ONCE, BEFORE THE SWEEP, AND NEVER INSIDE A LEG'S `command:`

A view root is git-ignored and never committed (ADR-0067 §6), so a fresh clone has none and the
unmutated control would be red — which the harness correctly reports as `NOT_MEASURED`, not as a
finding. So it must be generated first.

**It must not be generated by the leg.** Putting `skill-view generate` into a `command:` would
regenerate the very root the mutation just deleted, before the gate ever looked at it: every leg would
report the gate staying green over a tree that had been silently repaired, and `delete`, `retarget`
and `replace-with-file` would all become unmeasurable at once. That is exactly the fail-open shape
`skill-view-check.yml`'s own header names — *"Generate whatever is absent, then assert it is present"
would make `[absent-root]` unreachable and hand back a gate that cannot fail* — and it would be
committed here, in the file that exists to detect it.

`partial-view` would survive the mistake, because `generate` is a no-op over a root that already
resolves. **That is the trap**: three legs would go quiet and one would keep passing, so the sweep
would still look like it had run.

## Why these repos' legs are `kind: path`

The subject of a skill-root gate is the **shape of the tree**, and the defects it exists to catch —
an absent directory, a dangling symlink, a symlink checked out as a regular file, a view that resolves
but is INCOMPLETE — are not edits to any file. See `MutationKind.PATH` in `scripts/lib/mutation.py`,
and `#1842` for the three ways the harness did not fit before this.

## What is NOT here, and why

`FS.GG.Net/gate.yml`'s `bash scripts/skill-view selftest` step has **no leg**. `scripts/skill-view` is
both the tool and its own selftest — one kit-delivered file that prints its own tally — so a leg
mutating it and anchoring on that tally has `anchor.produced_by == target` and `load_specs()` refuses
it. **The refusal is correct** (`#1794`) and must not be worked around with a wrapper that re-emits the
tool's number under a second filename; that is anchor laundering. `#1830` measured that step by hand
and labelled it as by-hand; `#1842` AC5 is where it gets settled.
