# ADR-0064: `workBoard` — a single-repo, board-driven driver skill fills the fourth loop quadrant

- **Status:** Proposed
- **Date:** 2026-07-21
- **Affects:** FS-GG/.github (authors `workBoard` in its two skill roots, adds it to the `FS.GG.Drivers` package + `registry/driver-skill-manifest.json` + reconciled `registry/skills.yml`, publishes the driver package); FS.GG.SDD (bumps the `FS.GG.Drivers` pin and republishes `FS.GG.SDD.Cli`, which embeds the bytes and materializes them at scaffold time).
- **Interacts with:** [ADR-0053](0053-roadmap-driven-milestone-loop-disposable-sdd-subagents.md) (the disposable-subagent loop `workBoard` reuses); [ADR-0054](0054-workroadmap-delivery-fabric-a-github-authored-product-materialized-driver.md) (the `driver` class + the `FS.GG.Drivers` delivery fabric `workBoard` rides — `workBoard` is its second rider, as `drive-board` is `operator`'s first); [ADR-0057](0057-operator-scope-a-github-authored-never-materialized-skill-class.md) (the cross-repo `drive-board`, deliberately *not* materialized — `workBoard` is its single-repo counterpart); [ADR-0063](0063-scaffold-materializer-sources-skills-from-the-owner-repo.md) (owner-sourced driver bytes: a new driver skill "needs its `skills.yml` row and nothing else"); [ADR-0061](0061-collapse-the-publish-before-flip-schema-validator-split.md) (structural `scope` validation — why a new `driver` row is not schema growth); [ADR-0019](0019-org-repo-roster-registry-and-coordination-kit.md) (coordination-by-default wiring that puts the board tooling into a workspace); [ADR-0056](0056-sdd-is-the-default-lifecycle-spec-kit-is-legacy-and-scheduled-for-removal.md) (SDD as the default lifecycle the complex-item worker escalates into).

## Context

The org has two disposable-subagent loop skills. `workRoadmap` (ADR-0053/0054) burns down **one repo's markdown roadmap**, milestone by milestone, and is `scope: driver, materializes-when: always` — delivered into every scaffolded product workspace. `drive-board` (ADR-0057) burns down the **org Coordination board across every repo** and is `scope: operator, materializes-when: "false"` — never materialized, because it fans workers into sibling repos and a single product tree has no siblings.

That leaves one quadrant empty — **single-repo, board-driven** — and it is precisely the capability requested: a work loop *inside* a product workspace that drives that workspace's own project board to completion, or fails gracefully when it has none. Materializing `drive-board` cannot serve this (ADR-0057 is explicit: in a product tree it "cannot run" and its kit dependencies are absent), so the quadrant needs its own skill.

The enabling fact is that a coordination-wired workspace **already carries the board substrate**. `new-sdd-workspace` (`scripts/NewSddWorkspace/Program.fs`, coordination step, default ON) records the board identity as `FSGG_COORD_OWNER`/`FSGG_COORD_PROJECT` env in `.claude/settings.json`, vendors the `scripts/fsgg-coord` shim + `fs.gg.coord.cli` tool, and materializes `check-board`, `pnext-item`, and `intra-repo-parallel-work`. So the new skill can *compose* what is present rather than ship new tooling — and its absence (a `--no-coordination` workspace) is exactly the "fail gracefully" boundary.

## Decision

**Add `workBoard`: a `.github`-authored `scope: driver` skill, `materializes-when: always`, that drives a single product workspace's wired project board to completion via disposable per-item subagents, and refuses to run — cleanly — when the workspace is not board-capable.**

1. **It is a new skill, not a reclassification.** `drive-board` stays `operator`/never-materialized. `workBoard` is the single-repo sibling; the two share the reconcile → size-wave → spawn → verify-against-ground-truth → re-plan shape, differing only in fan-out (one repo vs. every repo) and ledger source (the wired board via `FSGG_COORD_*` vs. the org `Coordination` board).
2. **It targets the already-wired board.** `workBoard` reads `FSGG_COORD_OWNER`/`FSGG_COORD_PROJECT` (which `fsgg-coord` already consumes) and operates on *this repo's* items on that board. `new-sdd-workspace` is **not** taught to create a board; wiring-to-existing is the contract. (A `--create-board` option is a possible future ADR, not this one.)
3. **"Fail gracefully" is a runtime precondition, not a materialization gate.** `workBoard` always materializes (the coordination kit is wired *after* the scaffold materializer runs, so no scaffold-time predicate can see it), and at runtime it stops with one clear line — naming `workRoadmap` (markdown) or `new-sdd-workspace --board` as the fix — when the board env, the `fsgg-coord` engine, or `check-board`/`pnext-item` are absent, or when a workspace-owned (non-`FS-GG`) board outruns the engine (needs post-0.4.0, #1140).
4. **The worker is `pnext-item` with SDD-lifecycle escalation by item complexity.** Every item rides one `pnext-item` claim → worktree → PR → merge-on-green → done-stamp envelope. A simple item (Effort `S`/`M`) is implemented directly; a complex one (Effort `L`/`XL` or a `needs-sdd` signal) runs the full `fs-gg-sdd-*` lifecycle inside that envelope. Both skill sets are present in a wired workspace, so this is a documented branch, not new machinery.
5. **Delivery rides the existing driver fabric and is not schema growth.** `workBoard`'s bytes ship in the embedded `FS.GG.Drivers` package (ADR-0054/0063); `.github` adds the producer-manifest + reconciled `skills.yml` row and publishes `FS.GG.Drivers`; FS.GG.SDD bumps the pin and republishes `FS.GG.SDD.Cli`. Because `driver` already exists and scope validation is structural (ADR-0061), no `schemaVersion` bump, no validator publish-before-flip, and no `contract-coherence.yml` pin advance is required — the only versioned steps are the two package releases, ordered publish-before-re-pin.

## Consequences

- **The loop family is complete and named.** The 2×2 (single/cross-repo × markdown/board) is filled: `workRoadmap`, `drive-board`, and now `workBoard`; the empty cross-repo/markdown cell stays n/a. A future single-repo board loop variant is another `driver` row.
- **Product workspaces gain board-driven autonomy** without touching the org-operator path or the cross-repo `drive-board`.
- **`.github`'s `FS.GG.Drivers` package now carries two skills**; its producer-emitter and projection already generalize to N driver skills (ADR-0063), so the second rider needs a row and bytes, nothing structural.
- **FS.GG.SDD owes one re-pin + republish** so the bytes reach scaffolds; until that CLI is live, `workBoard` is authored but not delivered (publish-before-re-pin, the same ordering `workRoadmap` used).
- **Touch-set discipline becomes load-bearing inside one tree.** Unlike `drive-board`, `workBoard`'s workers share a working tree, so `intra-repo-parallel-work`'s `Paths:` disjointness (already enforced by `take`) is what keeps a wave from colliding — the skill must lean on it, not re-implement it.

## Alternatives considered

- **Materialize `drive-board` into workspaces (the literal request).** Rejected on the same structural grounds as ADR-0057: a cross-repo fan-out skill in a single-repo tree has no siblings to drive and no kit dependencies present. It would advertise an org-operator capability where it cannot run.
- **A `product` mode of `drive-board` (one skill, two modes) instead of a second skill.** Rejected: it overloads one skill with two incompatible run contexts (operator checkout vs. product tree) and two delivery classes (`operator` vs. `driver`) — the meaning-overload ADR-0054/0057 repeatedly refuse. Two skills each say one true thing.
- **Extend `workRoadmap` to optionally read a board instead of markdown.** Rejected: it doubles `workRoadmap`'s ledger contract and its "locate the roadmap file" logic, and couples a markdown-lifecycle skill to the board/`fsgg-coord` substrate that may be absent. A board loop and a markdown loop are cleaner as siblings than as one skill with a mode switch.
- **Teach `new-sdd-workspace` to create a per-workspace board now.** Deferred, not rejected: the requested capability only needs a *target* board, which the wiring already provides. Board creation is a larger, separable enhancement (a `gh project create` + env write) and would be its own ADR.
