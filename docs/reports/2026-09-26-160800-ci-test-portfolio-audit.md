# CI test portfolio: remove duplicate execution and reduce job overhead

**Observed:** 2026-09-26, approximately 15:59–16:08 UTC. **Status:** analysis and proposed follow-up changes; no workflows, tests, required checks, or release authority changed by this report.

The best first changes are to stop duplicate branch/PR CI in FsQuint, retire receiver jobs that only print a compatibility message, and remove repeated fixture/build invocations while retaining their assertions. Game and Governance have the clearest opportunities to combine restore, build, and test work. Coordination has the largest measured workload, but its bootstrap and coherent evidence have different consumers; deleting either pipeline is not justified by similar test names.

Queue delay dominates several recent product runs. Game used **13.87 runner minutes across 27 jobs**, yet took **326.90 minutes** from workflow creation to the last job completing. Rendering used **28.65 runner minutes across 14 jobs**, yet took **276.53 minutes**. Reducing tiny jobs can improve scheduling pressure even when the runner-minute saving is small. These observations do not prove which other workload caused the delay.

## Scope and measurement

The authenticated organization listing returned **17 repositories**, all non-archived and non-fork. This audit includes the main products, authority and substrate sandboxes, and all four SVG qualification workspaces, including an empty repository. Coverage is all repositories visible to this credential; the listing alone does not establish visibility into any inaccessible private repository.

Collection used GitHub repository metadata, paginated workflow inventory, the latest 100 workflow runs per repository (or every retained run when fewer existed), the latest five runs of each active workflow, immutable default-branch source archives, classic branch protection, and effective rulesets. Job/step metadata was fetched for the latest success and failure found within each five-run workflow sample; workflows without either contributed their latest run. Additional reads covered in-flight Coordination runs, retained history in repositories with no active workflow, and all 32 FsQuint push/PR pairs. The appendix identifies workflows with no sampled execution instead of assigning zero cost.

The final inventory contains **239 active workflows**. The expanded job sample contains **342 runs and 659 materialized job records**; some records were skipped or still running. This is a bounded portfolio audit, not a historical census or a test-case coverage/mutation study. Recent samples are unequal in age: `.github`'s initial 100 runs span roughly two hours, while dormant release workflows reach back into August. Counts and failures must not be compared as frequency estimates across those windows.

- **Runner minutes:** sum of `completed_at − started_at` for jobs with an assigned runner and both timestamps; skipped/unassigned jobs contribute no measured execution. These are execution durations, not invoiced minutes, OS-weighted charges, or money.
- **Materialized jobs:** actual job records returned by the run/jobs API, including skipped jobs. They differ from YAML job keys, matrix entries, queued workflow counts, and runner usage.
- **Start delay:** job creation to start. It is a scheduling-delay proxy; it can include orchestration and concurrency waiting. Summing it across parallel jobs does not yield developer wait or recoverable runner time.
- **Workflow elapsed:** creation to last completed job, used only for completed runs. Run conclusions, job snapshots, source snapshots, and branch rules were read sequentially, not atomically.
- Source links use captured default-branch SHAs. Historical run links refer to their own candidates, which can differ from those SHAs. Costs establish observed opportunities, not a benchmark of every current default-branch implementation.

## Evidence behind the priorities

### FsQuint runs both branch and PR qualification

[FsQuint CI](https://github.com/FS-GG/FsQuint/blob/bebcdeb5cbbeeebab5fb7765346ff85565c055f2/.github/workflows/ci.yml) declares unrestricted `push` and `pull_request`, `contents: read`, one `qualify` job, and no privileged PR-target execution. Its 80 recorded CI runs contain **32 source-head pairs** with both event types. For example, [push run 36144418812](https://github.com/FS-GG/FsQuint/actions/runs/36144418812) and [PR run 36144449454](https://github.com/FS-GG/FsQuint/actions/runs/36144449454) report the same source head `0e35a57bd5`. All 32 paired push jobs were fetched to obtain the 23.12-minute total; it is not extrapolated from one run.

A PR checkout normally tests its synthetic merge, while the branch push tests its source branch. The two events therefore are not guaranteed byte-identical checkouts even when the API's head SHA matches. The proposal chooses PR integration plus protected/default-branch integration as the ordinary route; it does not certify one event's receipt as the other's evidence. The captured main protection endpoint returned “Branch not protected,” and the effective-rules endpoint returned an empty list. A fork still receives the same read-only `pull_request` workflow, subject to GitHub's existing approval policy; no credential broadening or `pull_request_target` substitution is proposed. Retain package-consumer isolation and the independent CI preflight example inside `eng/check.sh` and its caller.

### Receiver compatibility contexts consume jobs without validating a subject

[The shared contract-coherence workflow](https://github.com/FS-GG/.github/blob/7a42d4a39c7a70dbd8fd2694a81aa8199ca39e19/.github/workflows/contract-coherence.yml) has a real registry/props verifier only when `github.repository == 'FS-GG/.github'`. Other callers execute the “Receiver boundary” echo and skip checkout, tool setup and validation. The observed receiver job durations include **5 seconds in Game**, **3 seconds in Rendering**, and **3 seconds in Governance**. Removing unrequired callers loses no executed assertion. It also avoids an extra runner request during the multi-hour queue episodes.

Net and Governance explicitly require `contract-coherence / coherence` in classic branch protection. Removing those callers first would strand their PRs. Retire those two compatibility requirements through an explicit protection change after confirming the real receiver obligations remain covered. `kit / coordination-kit`, receiver materialization, build-config drift and root visibility are different checks and must not be inferred redundant from their names: [coordination-coherence](https://github.com/FS-GG/.github/blob/7a42d4a39c7a70dbd8fd2694a81aa8199ca39e19/.github/workflows/coordination-coherence.yml) compares committed bytes to the receiver's pinned package, while skill-view tests exercise generation, rejected arguments and runtime visibility.

### A fixture can be duplicated while its live checker remains essential

[The policy subject registry](https://github.com/FS-GG/.github/blob/7a42d4a39c7a70dbd8fd2694a81aa8199ca39e19/policy/subjects.json) declares `projection-fixture`; [coherence](https://github.com/FS-GG/.github/blob/7a42d4a39c7a70dbd8fd2694a81aa8199ca39e19/.github/workflows/coherence.yml) independently runs exactly `bash tests/projection/run.sh` before the live projection checker. On overlapping workflow changes, the broad policy job and the required projection job repeat that fixture. Removing only the broad policy invocation preserves the candidate's required negative-control evidence. The whole sampled [policy run](https://github.com/FS-GG/.github/actions/runs/36253015506) took 28 seconds, so the saving is too small to justify a new workflow or receipt protocol.

SDD's [gate](https://github.com/FS-GG/FS.GG.SDD/blob/cb89bcafb95efa1d11ecd29c21ca4108cd30a2cf/.github/workflows/gate.yml) and [skill-view-check](https://github.com/FS-GG/FS.GG.SDD/blob/cb89bcafb95efa1d11ecd29c21ca4108cd30a2cf/.github/workflows/skill-view-check.yml) repeat the same four `skill-view generate` rejection cases. Centralize the fixture invocation, but preserve integration generation inside the larger gate. Its materializer write-set, binary compatibility, custody mutations, locked package acceptance and working-tree cleanliness checks test different failure modes.

### Game has both reusable build work and many very small jobs

[Game gate](https://github.com/FS-GG/FS.GG.Game/blob/d399c36f35a2f85a669a7bc7c37eed0b98896a03/.github/workflows/gate.yml) separately restores/builds the same Debug solution in the deterministic-build and invariant jobs, while the full-suite job invokes `dotnet test` with build enabled. The invariant subset is exercised again with filters to prove the constraint tests still exist and match; the zero-match check is valuable even when full-suite membership overlaps. Preserve that assertion when combining execution.

In [Game run 36189708708](https://github.com/FS-GG/FS.GG.Game/actions/runs/36189708708), standalone build jobs took **42 seconds on Linux and 77 seconds on Windows**. Invariant jobs took **40 and 85 seconds**; the invariant execution steps themselves took **6 and 10 seconds**. The full suites took **84 and 102 seconds**. Sharing restore/build inside each OS job is a stronger saving candidate than deleting the second OS or dropping invariant coverage.

Seven hermetic fixture jobs—skill refs, packed API surface, pin coherence, skill-ref sweep, composite-action lint, FSI doc surface, and harness selftest—together occupied **43 seconds** but materialized seven runners. Batch their commands with distinct step names and fail correctly if any fails. The live lint, package-consumer and documentation-typecheck checks still cover different subjects. In particular, the .NET, Fable and browser lockstep consumer matrix checks deployed runtime behavior and package consumption; it is not interchangeable with the headless source test suite.

### Governance repeats Debug compilation and reference-gate execution

[Governance gate](https://github.com/FS-GG/FS.GG.Governance/blob/9a32eb8393813829b42fb4934aa1458758ed4009/.github/workflows/gate.yml) runs a cold Debug build, full Debug tests, full Release tests, a reference-gate project build/test, and an advisory API check that builds again. [build.fsx](https://github.com/FS-GG/FS.GG.Governance/blob/9a32eb8393813829b42fb4934aa1458758ed4009/build.fsx) makes the full-suite command target the entire solution, and that solution includes `FS.GG.Governance.ReferenceGateSet.Tests`. This proves project-level overlap with the dedicated reference guard, not that every test's environment and pack side effects are identical.

In [Governance run 36135311721](https://github.com/FS-GG/FS.GG.Governance/actions/runs/36135311721) the Debug build took **242 seconds**, Debug full suite **537 seconds**, Release suite **399 seconds**, reference guard **122 seconds**, and advisory API compatibility **281 seconds**. The first consolidation should share Debug build products within one execution boundary and preserve bounded MSBuild parallelism. Keep Release coverage: the source records an actual Release discovery/crash failure class. Pack byte identity, gate presence and version assertions must remain visible even if their tests execute once through the full suite.

## Coordination: optimize the workload without erasing evidence

[Optimistic validation run 36251147723](https://github.com/FS-GG/FS.GG.Coordination/actions/runs/36251147723) used **145.18 runner minutes**, materialized **32 jobs** (31 assigned runners, one skipped), and completed in **29.95 minutes**. The formal-base shard took **17m13s**; nonformal partition 3 took **11m13s**, partition 0 **8m13s**, partition 2 **42s**, partition 4 **58s**, and partition 5 **77s**. Duration-aware partitioning is worth a bounded experiment, but moving obligations must preserve their isolation contracts, plan identity and aggregate completeness. Splitting or merging formal shards also changes receipt expectations and requires producer qualification; it is not a YAML-only savings edit.

The sampled successful [Bootstrap run 36252968857](https://github.com/FS-GG/FS.GG.Coordination/actions/runs/36252968857) used **33.38 runner minutes** across ten started jobs out of fifteen materialized records, finishing in **13.43 minutes**. These two examples have different candidate SHAs and must not be added as one candidate's cost. [The bootstrap compiler script](https://github.com/FS-GG/FS.GG.Coordination/blob/145afceae3a55fd351df402f62542fa3d0c1ed7a/eng/bootstrap-gates/compiler-and-tests.sh) explicitly runs unit, orchestration-host and architecture projects; the optimistic plan also covers compiler/unit and other obligations, but shares prepared outputs and emits different receipts. A deduplication proposal needs an explicit producer/consumer obligation map, exact candidate identity, profiles/bounds, provenance and freshness validation, and fail-closed missing/malformed/late-failure behavior before a legacy execution can be replaced.

At separate later job reads, run `36252918184` exposed **30 materialized jobs: eight queued, six running, sixteen completed**; run `36253424804` exposed **30: fourteen queued, six running, ten completed**. Their earlier workflow-list records both said queued. This demonstrates why a queued workflow is not a count of queued runners and why admission decisions need job state. The reads were non-atomic and are not a simultaneous organization-wide queue total.

The applicable [ADR-0084](https://github.com/FS-GG/.github/blob/7a42d4a39c7a70dbd8fd2694a81aa8199ca39e19/docs/adr/0084-semantic-reuse-never-cancels-coherent-validation.md) requires a complete coherent detector even when authenticated semantic reuse advances delivery. Reuse does not authorize cancellation. Never propose these as free optimizations: cancelling accepted coherent candidates, weakening verification bounds, replacing negative-control executions with source grep, dropping packet/custody checks, equating cache hits with qualification, or reusing unrelated candidate success. Reducing redundant bootstrap/coherent execution would require a new or amended evidence-consumer contract; reducing a no-op receiver job does not.

## Verify a pilot before expanding it

For each implemented change, compare the same candidate and toolchain where possible, with cold and warm setup recorded separately. Capture materialized/started jobs, execution minutes, creation-to-start delay, time to the last required result, and failures. Keep test counts and negative-control assertions, while distinguishing source tests from installed/packed consumer tests. Require real nonzero exits and artifacts on failure, and make a missing test selection or receipt fail closed.

A one-repository pilot should show the expected command/job removal and preserved results before expansion. Do not promise a percentage reduction from these heterogeneous samples. There is no priced runner model, defect-yield history, test-case flake classification or retention-cost measurement here; those inputs remain unknown. The known tiny invocations and no-op jobs can be addressed without first building a new telemetry service.
