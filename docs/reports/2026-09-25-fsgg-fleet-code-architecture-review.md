# FS-GG fleet code and architecture review

**Review date:** 2026-09-25. **Scope:** the 17 repositories returned by the authenticated FS-GG organization listing, their tracked default-branch source and tooling, and representative workflow/receiver entry points. This listing is not the authoritative receiver roster: [`FSC-00 census draft #3700`](https://github.com/FS-GG/.github/pull/3700) maps nine organization repositories into `registry/repos.yml`, one into `outside-fabric`, and seven without a roster disposition; the registry's tenth row is an external, non-participant repository. Private qualification identifiers are withheld from this public review. `.github` protected main was `ff425734d277fa54c3d71601da90fe7b22619c15`; `FS.GG.Coordination` protected main was `a68550435cf1b6037b1e02ea90f91883428d0d92` at inspection. Other local repositories were inspected at their tracked main trees; remote-only repositories through GitHub read APIs. Worktree drafts and open PRs were not counted as protected behavior.

The review is static architecture and executable inventory with two disposable defect reproductions. It is not a penetration test, a full hosted-CI run, a production load test, or a secret audit. The [migration design and roadmap](../coordination/2026-09-25-fsharp-automation-convergence-design-and-roadmap.md) owns prospective work; the [V2 roadmap](../github-substrate-v2-roadmap.md) owns cutover acceptance.

## Architecture verdict

The fleet already has substantial F# domain code. The main language-convergence opportunity is at the automation edge: Python and shell scripts parse manifests, enforce organization policy, compose providers, stage packages and report receipts. Porting this logic is useful when it removes duplicated policy or makes a contract typed and independently testable. A blanket removal target would erase valuable independent Python oracles, platform bindings and small shell launchers while adding migration risk to the V2 cutover.

The intended boundary is owner-specific:

| Owner | Current boundary and review verdict |
|---|---|
| `.github` | Owns organization registry, pins, policy, desired-state projections, V1 control-plane code and workflows. Some policy scripts are multi-thousand-line programs. Put new enduring F# policy in an owner-specific project without V1-only runtime dependencies. GS2-14 removes V1 paths after exact inventory; it does not require deleting every `FS.GG.Coord.*` project. |
| `FS.GG.Coordination` | Owns the typed Quint-driven V2 protocol, Core, GitHub adapters, CLI/application and qualification. Python operational hosts are significant but include protected grant, Git and recovery behavior; optional rewrites should normally follow OperatingV2. |
| `FS.GG.SDD` | Owns published generic Contracts/Artifacts/CLI primitives. It is the candidate producer for shared manifest and staging mechanics, not a new home for every repository's policy. |
| `FS.GG.Templates` | Owns provider composition and generated workspace content. Its typed tool should decide effective providers and stage exact bytes; receiver shell remains part of the generated interface where needed. |
| Product repositories | Rendering, Game, Audio, Governance and Net own their product checks, release rosters and local policy. Share only generic primitives and preserve independent tests. |
| Authority and sandbox repositories | Hold state or synthetic qualification targets. Adding general F# tooling there would blur authority and increase attack surface without a demonstrated benefit. |

The older [`.github` architecture review](2026-07-25-194615-comprehensive-code-architecture-review.md) identified a broad legacy CLI composition edge. That observation remains relevant, but new policy should not deepen a V1 package scheduled for removal.

## Conversion constraints and next evidence

- A `.github` policy port must keep separate PR versus live-main/feed subjects, complete population enumeration, unavailable-feed refusal, wrong-pin/unknown-producer controls, exact output contracts and independent mutation evidence. Rule (a) parity uses the corrected filtered/unfiltered and signed-shape behavior only after #3698 is accepted; source-only parity does not prove an installed receiver.
- Generic artifact code can share path validation, archive/hash, stable serialization and staged-byte verification. It must not erase owner-specific digest normalization, release rosters, producer provenance or credential policy. Rendering's release custody demands an exact 19-archive population; FsQuint can legitimately read back a previously published version without local archives.
- Coordination's operation adapters require wrong key, wrong target/grant, stale lease, missing page, duplicate attempt, lost response and secret-output controls. Preserve the native Git and Linux boundary until a replacement passes an isolated installed operation. Do not dual-run production writers.
- The previous telemetry helper [proposal](2026-09-04-fsharp-roadmap-telemetry-and-projection-automation-design.md) names four Python files absent from current main; `Telemetry.fs` and `RoadmapWorkUnit.fs` already exist. Map only remaining requirements to current owners and accepted evidence. Inventory Contracts/Store's Core dependency and Store's historical CLI-path source link; resolve V1-only code for Q9 without making optional helper ports a V1-retirement gate. Host and dashboard successor work has its own roadmaps.
- Keep all selected source, package, lock, registry, workflow, receiver and settings changes inside the GS2-10 candidate. The optional migration track must not delay GS2-11 after true cutover prerequisites pass or become a condition for V1 retirement.
