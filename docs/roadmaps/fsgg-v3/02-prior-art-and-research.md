# FS.GG v3: prior art, operational experience and design synthesis

Research date: 2026-10-10. This appendix informs the [v3 design](../2026-10-10-fsgg-v3-clean-rewrite.md); it does not amend current operating policy.

## Method and limits

The research followed the [source analysis and initial draft](01-framework-analysis-and-initial-draft.md). It covers repository structure, modularity, durable execution, agent coordination, developer platforms, build selection, provenance, formal methods and rewrite risk. Sources are original engineering reports, author essays, research publications or official implementation documentation. Search snippets were used for discovery; linked pages were opened and relevant sections inspected. Documentation is mutable and describes the version available on the research date, not necessarily the dependencies that v3 will select after v2 completion.

Experience reports explain mechanisms and tradeoffs; they are not controlled comparisons. Vendor documentation establishes intended semantics, not proof of operational success. Survey correlations do not establish causation. Large-company results are not projected numerically onto FS.GG. No source reviewed demonstrates that a one-shot FS.GG rewrite will succeed; that delivery constraint comes from the product owner.

## Repository and modularity experience

| Source | Reported experience or finding | Application and limitation |
|---|---|---|
| R01 — Google, Potvin and Levenberg, 2016, [single-repository experience](https://research.google/pubs/why-google-stores-billions-of-lines-of-code-in-a-single-repository/) | A shared source repository supports common visibility and coordinated changes, backed by substantial specialized tooling. | Put components that change together in one platform repository. Google's scale and infrastructure do not justify building a custom source-control system for FS.GG. |
| R02 — Shopify, 2020, [modular monolith retrospective](https://shopify.engineering/shopify-monolith) | Eighteen months after the earlier account, most implementation details had changed. Prescribed interface patterns sometimes added friction without solving developers' problems. Static dependency analysis gave more actionable feedback than expensive runtime call graphs. The team emphasized change locality. | Enforce a small acyclic dependency graph with F# signatures and build references. Judge boundaries by common changes, not folder aesthetics. This was an incremental Rails effort, not evidence for a single-cutover rewrite. |
| R03 — Segment, historical engineering report hosted by Twilio, [Goodbye Microservices](https://www.twilio.com/en-us/blog/developers/best-practices/goodbye-microservices) | Separate destination services initially provided isolation, then multiplied shared-library deployments and operational work. Consolidation improved their development and operations, while weakening fault isolation and changing cache behavior. | Consolidate the trusted control plane; retain separate runner processes for code execution. This experience concerns one pipeline, not a universal verdict against services. The article's editorial AI summary was not used as evidence. |
| R04 — Uber, 2020, [Go monorepo and Bazel](https://www.uber.com/us/en/blog/go-monorepo-bazel/) | Adoption required build-rule work, target-impact tooling, upstream contributions and IDE integration work. Large target lists exposed practical limits in existing interfaces. | Budget for affected-build selection and developer ergonomics. Start with the .NET build graph already available; do not select Bazel merely because another monorepo uses it. |

These cases support consolidation when release coordination and shared changes dominate. They also expose its costs: shared dependency upgrades, wider failure domains, slow CI and central tooling ownership. The proposal therefore chooses a **platform monorepo and modular control plane**, while keeping execution isolation and product runtime independence explicit.

## Durable workflows, actors and external effects

| Source | Relevant semantics or experience | Application and limitation |
|---|---|---|
| R05 — Akka.NET, [reliable delivery documentation](https://getakka.net/articles/actors/reliable-delivery.html) | Default delivery is at most once. Reliable delivery introduces acknowledgements, optional durable producer queues, flow control and possible duplicate delivery during recovery. | Treat actors as scheduling/supervision machinery. Persist business intent and deduplicate commands independently of mailbox delivery. Message acknowledgement is not proof of a GitHub mutation. |
| R06 — Temporal, [workflow definition and determinism](https://docs.temporal.io/workflow-definition) | Replay requires deterministic workflow commands. External interactions belong in activities; changes to running workflow definitions require versioning discipline. A [.NET SDK](https://docs.temporal.io/develop/dotnet) is available. | Temporal is a credible alternative to maintaining custom durability. Compare one real failure-heavy vertical slice before fixing the runtime choice. Do not layer Temporal and an authoritative Akka journal over the same workflow. |
| R07 — Uber, 2019, [ticket routing workflow experience](https://www.uber.com/gb/en/blog/customer-obsession-ticket-routing-workflow-and-orchestration-engine/) | Fragmented routing code remained difficult to reason about despite high test coverage. Separating task implementation from coordination improved clarity. Early designs hid too much control logic in scoring, then put too much detail into the workflow. | Keep prerequisites and meaningful branches visible in the compiled plan; keep provider details inside adapters. The useful lesson is task/control separation, not the article's broad execution-guarantee language. |
| R08 — Uber, [Cadence architecture overview](https://www.uber.com/us/en/blog/open-source-orchestration-tool-cadence-overview/) | Durable workflow execution has dedicated history, matching and storage machinery, alongside application workers. | Managed durability can remove application plumbing, but adds an operational dependency. The overview is explanatory material, not a cost comparison with FS.GG's PostgreSQL runtime. |
| R09 — AWS Builders' Library, [idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) | Caller-supplied request identity, retained results and rejection of reused identity with different parameters make retries less ambiguous. Retention and late requests require explicit treatment. | Persist operation identity plus parameter digest. Retrying an operation retains its identity; changing its intent creates another operation. Upstream APIs without this contract still require observation and possibly manual resolution. |
| R10 — AWS Builders' Library, [timeouts, retries and jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) | Timeouts do not prove that effects did not happen. Retries can amplify load; backoff, jitter and bounded retry policy address different failure modes. | One retry owner per effect, bounded original deadlines, provider-specific observation, and jittered polling. “Optimistic” development does not mean blindly repeating writes. |
| R11 — Kubernetes, [controllers](https://kubernetes.io/docs/concepts/architecture/controller/) | Controllers reconcile observed state toward desired state through repeated control loops. | Use reconciliation for board projections, work recovery and publication observation. This does not require running Kubernetes or expressing the platform as custom resources. |
| R12 — Microsoft, [Orleans grain persistence](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-persistence/) | Grains can persist state through storage providers or access databases directly; persistence has explicit read/write and failure semantics. | Virtual actors are another implementation option, not an automatic durable business workflow. Changing actor libraries would not remove effect identity, reconciliation or GitHub integration work. |
| R13 — LangGraph, [persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | Checkpointers preserve thread state; stores preserve cross-thread data. In-memory checkpointing does not survive process restart. | Agent conversation memory may remain provider-owned. It must not compete with the platform's accepted plan and external-effect ledger. A checkpoint does not by itself establish the result of a timed-out external write. |

The recommended default remains Akka.NET plus PostgreSQL because the inspected code already embodies useful durable-effect semantics. This is an **inference from FS.GG's existing investment**, not evidence that custom workflow infrastructure is intrinsically cheaper. The roadmap contains an early bounded comparison against Temporal; if the custom runtime cannot meet the common failure tests without expanding into a general workflow product, select Temporal before dependent implementation spreads. The final system has one workflow authority either way.

The [Akka.NET repository license](https://github.com/akkadotnet/akka.net/blob/dev/LICENSE) is the relevant upstream license source (R14). Do not apply assumptions about the separate JVM Akka product. The actual dependency lock and license notices should be checked at implementation time; this research does not select a future package version.

## Developer platforms, product packs and agents

| Source | Experience or mechanism | Application and limitation |
|---|---|---|
| R15 — Spotify, 2020, [golden-path experience](https://engineering.atspotify.com/2020/08/how-we-use-golden-paths-to-solve-fragmentation-in-our-software-ecosystem) | Supported paths helped onboarding. Long tutorials exposed too many real steps; the platform needed to shorten the path itself. Documentation ownership and purpose also needed adjustment. | Product packs own a complete supported journey and its examples. Reduce commands and manual joins instead of merely shortening instructions. This is a qualitative company account. |
| R16 — Backstage, [software template model](https://backstage.io/docs/features/software-templates/writing-templates/) | Templates combine metadata, parameters, executable actions and outputs. Secret inputs are handled separately from ordinary parameters. | Use a typed pack manifest with parameters, actions, skills and conformance fixtures. Borrow the abstraction without requiring a Backstage deployment or letting arbitrary template code execute in the privileged Host. |
| R17 — DORA, [platform engineering synthesis](https://dora.dev/capabilities/platform-engineering/) and [2024 report](https://dora.dev/research/2024/dora-report/) | Platform benefits coexist with possible throughput and stability problems. Developer independence and clear task feedback matter. The synthesis cautions against oversized, late platform releases. | Measure complete user journeys and human intervention. Build and test complete slices internally before the single cutover. Survey associations are not promises of a particular productivity gain. |
| R18 — Anthropic, 2024, [building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | The authors distinguish predefined workflows from agent-directed processes, recommend starting simply, and describe debugging costs from unnecessary abstractions. | Use deterministic platform control flow around bounded agent tasks. An agent can propose a plan change; it cannot silently redefine authority or completion. These are vendor engineering recommendations. |
| R19 — Anthropic, 2025, [multi-agent research system experience](https://www.anthropic.com/engineering/multi-agent-research-system) | The team encountered duplicated work, over-delegation and high token consumption. Clear task boundaries and outcome-based evaluations mattered. It explicitly notes that many coding tasks are less parallelizable than research. | Expose dependency-ready tasks, bounded concurrency and explicit outputs. Parallelize independent modules and checks; avoid mandatory planner/reviewer/critic chains for routine changes. Their research benchmark is not a coding-throughput forecast. |

The implication for low-bureaucracy development is concrete: the platform handles workspace creation, exact identities, test selection, evidence capture and PR reporting automatically. The contributor supplies intent and reviews the resulting change. A new product pack should not require learning the scheduler internals or a series of producer publication ceremonies.

## CI, GitHub, provenance and formal verification

| Source | Technical constraint | Application and limitation |
|---|---|---|
| R20 — GitHub, [required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) | Path-skipped required workflows can remain pending. Merge-queue checks need the appropriate merge-group event. Required results belong to the relevant commit. | Always run a small classifier and final required aggregator; select jobs inside that envelope. Recheck the actual candidate head or merge group. Do not represent skipped obligations as successful execution. |
| R21 — GitHub, [webhook practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks) | Authenticate deliveries, acknowledge quickly, queue work, and use delivery IDs; redelivery can reuse the same delivery identifier. | Durable inbox plus deduplication and periodic reconciliation. A webhook is a notification to inspect facts, not an infallible ordered command log. |
| R22 — GitHub, [GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api) | Rate, resource and query limits apply independently of application workflow needs. | Bound and paginate queries; distinguish partial/unavailable observations from empty populations. Avoid a poller per agent and unrestricted board-wide refreshes. |
| R23 — Microsoft, [MSBuild process and graph](https://learn.microsoft.com/en-us/visualstudio/msbuild/build-process-overview) | Build evaluation includes project references, imports, properties, environment and target execution. Graph builds make project references explicit scheduling inputs. | Derive .NET impact from the actual graph plus shared inputs; add pack-to-template/conformance dependencies. A path-only classifier is insufficient. |
| R24 — Bazel, [hermeticity](https://bazel.build/basics/hermeticity) | Repeatability requires controlled inputs and tools; ambient system binaries and source-tree writes are common sources of non-hermetic behavior. | Pin tools and isolate build outputs before investing in remote caches. Adopting the principle does not establish that all v3 builds are already hermetic. |
| R25 — SLSA, [provenance](https://slsa.dev/spec/v1.2/provenance) | Provenance describes where an artifact came from through its build chain. | Bind candidate artifacts to source, toolchain and build identity. Provenance is not proof of correct behavior or successful consumer installation. No SLSA level is claimed by this proposal. |
| R26 — Amazon, 2015, [formal methods experience](https://www.amazon.science/publications/how-amazon-web-services-uses-formal-methods) | Engineers used specification and model checking to expose difficult design errors in critical systems. | Spend formal effort on concurrency, cancellation, fencing and unknown effects. This does not justify model-checking ordinary prose or treating model validity as implementation proof. |
| R27 — Quint, [model-based testing](https://quint.sh/docs/model-based-testing) | Model traces can drive implementation tests; implementation correspondence remains a separate problem from validating the model. | Connect typed-SDD invariants to reducer tests and real adapter fault injection through FsQuint. Keep modeled assumptions visible. Exhaustiveness claims require explicit bounds and verified correspondence. |

## Evidence that challenges the requested rewrite strategy

R28 — Joel Spolsky's 2000 essay, [Things You Should Never Do, Part I](https://www.joelonsoftware.com/2000/04/06/things-you-should-never-do-part-i/), argues that rewrites discard hard-earned behavior embedded in existing code and can delay delivery substantially. This is an influential practitioner argument, not a controlled study of all rewrites. Together with DORA's platform guidance, it is a substantive warning against an open-ended “build everything, then discover whether it works” programme.

The requested delivery policy remains a complete rewrite and single replacement, with no backward compatibility. The response to that risk is a finite capability scope, preserved behavioral scenarios, early end-to-end tests in isolated environments, a working integrated v3 main branch throughout development, and a cutover that starts with no unsettled v2 work. There is no gradual production replacement, migration facade, dual writer or live shadow dispatcher.

## How research changed the initial draft

| Initial idea | Refined decision | Evidence that changed or constrained it |
|---|---|---|
| A logical monorepo | Platform-only monorepo with enforced boundaries and change-locality measurements | R01–R04: colocation alone is insufficient; tooling and coupling costs remain |
| Akka orchestrates the pipeline | Pure compiler/reducer plus one durable authority; bounded early alternative comparison | R05–R13: delivery, state persistence and effect settlement are different guarantees |
| Product-specific materials are packages | Cohesive product packs with supported journeys, conformance tests and separate execution trust | R15–R17: adoption depends on useful paths and independence, not catalog size |
| Aggressive parallel development | Dependency-based parallelism with minimal shared locks and measured conflict/rework cost | R19 and local source boundaries: more agents do not imply more independent work |
| Typed-SDD governs development | One accepted semantic model, automated evidence, verification proportional to change | R26–R27 and inspected SDD contracts: formal modeling needs implementation correspondence |
| One-shot replacement | One production cutover after repeated internal whole-system qualification | R17/R28: complete replacement is a product constraint, not a research-proven advantage |
| Simpler releases in a monorepo | Atomic internal source changes; immutable release candidate, external installation proof still required | R20/R23–R25 and local publication history: source coherence does not prove package usability |

## Alternatives explicitly not selected

An all-organization monorepo would include product runtime libraries whose changes do not always coincide with the platform. It remains possible later, but is outside this rewrite's dependency-reduction objective. A microservice per logical module would preserve distributed delivery overhead without a demonstrated isolation or scaling need. A second workflow engine inside an agent SDK would duplicate operational authority. A mandatory portal, Kubernetes cluster, general plugin marketplace, custom build engine or learned scheduler would expand the critical path without resolving the observed composition problem.

Revisit these choices only against a concrete unmet requirement and measured workload. The [roadmap](03-delivery-roadmap.md) assigns the remaining runtime, scope and performance decisions to early experiments rather than leaving them as late integration surprises.
